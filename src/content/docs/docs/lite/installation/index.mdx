TBMQ Lite is the single-node edition of TBMQ: one container and one data volume, with no Kafka, PostgreSQL or Valkey
beside it. It keeps TBMQ's MQTT 3.1, 3.1.1 and 5 handling, persistent sessions with durable offline queues, retained
messages, all five authentication providers, the REST API and the web UI, and stores everything in an embedded
database on the volume. It supports **DEVICE** clients only. To see how it differs from clustered TBMQ, read
<DocLink product={Products.TBMQ_LITE} path="lite-vs-tbmq">Lite compared with TBMQ</DocLink>.

## Supported hosts

- **Linux with Docker Engine**, on `linux/amd64` and `linux/arm64`. One image serves both architectures.
- **64-bit Raspberry Pi OS** is supported but not tested in the beta. A 32-bit OS cannot run the image.
- **Windows and macOS** through Docker Desktop, for development. Use a named volume, as in the commands below.
  These hosts are not tested in the beta.

The broker is sized for a container with {LITE_CAPACITY.reference.containerInText} of memory; it also starts in less. See
<DocLink product={Products.TBMQ_LITE} path="guarantees-and-limits">Guarantees and limits</DocLink> for the
measured capacity.

### The data volume

Everything the broker keeps lives under `/data`: the store in `/data/db` and the checkpoints taken before an upgrade in
`/data/backups`. The command above mounts the named volume `tbmq-lite` there, so the data survives when the container
is removed. Without a volume, removing the container deletes all data.

The broker runs as the non-root user with uid and gid `799`. A named volume needs no preparation. A bind mount must be a
directory that uid `799` can write, otherwise the broker cannot open its store:

## First sign-in

Open **http://localhost:8083** (or the host's address) and sign in as the system administrator:

- **Username:** `sysadmin@thingsboard.org`
- **Password:** `sysadmin`

The broker does not let this password in: it asks for a new one at once. The new password must meet the password
policy and may not be `sysadmin`. After you set it, you are signed in.

<Aside type="caution">
  Until someone sets that new password, whoever reaches port `8083` first and signs in with `sysadmin` takes the
  account. If the port is reachable by others, set the password at install time instead.
</Aside>

To start with a password of your own, set `TBMQ_ADMIN_PASSWORD` on the first start:

<Code code={runCmdPassword} lang="bash" />

- It applies only when the broker creates the system administrator, that is, on the first start with an empty volume.
  Changing or removing the variable later does nothing; change the password in the UI from the account's profile instead.
- It is used exactly as set, without trimming. It must be 6 to 72 characters long, at most 72 bytes in UTF-8, and not
  `sysadmin`, otherwise the broker does not start and the log names the variable.

Administrators you add later on the **Users** page with the default password are also asked to change it at their first
sign-in.

After signing in, continue with
<DocLink product={Products.TBMQ_LITE} path="getting-started">Getting started</DocLink>.

## Logs, health and stopping

The broker logs to standard output:

```bash
docker logs -f tbmq-lite
```

The first line shows what the start script read from the container's limits and which JVM settings it chose, for example:

```text
TBMQ Lite: memory 2048 MiB, CPUs 2 (cgroup v2), collector G1, max direct memory 204 MiB, jemalloc on
```

The image has a Docker health check, so `docker ps` shows the container as `healthy` once the broker is up. It
requests `/actuator/health` on the HTTP port inside the container and passes when the status is `UP`. It follows
`HTTP_BIND_PORT`, and `HTTP_BIND_ADDRESS` when that names one address. It needs the default actuator base path. With
`SSL_ENABLED=true` (HTTPS on the HTTP port) it only checks that the port accepts a connection. To turn it off, run the
container with `--no-healthcheck`, or set `healthcheck: disable: true` in Compose.

Stop and start the broker with `docker stop tbmq-lite` and `docker start tbmq-lite`. Docker's default stop timeout of
10 seconds covers the broker's shutdown, which waits up to `STANDALONE_SHUTDOWN_DRAIN_TIMEOUT_MS` (4 seconds by
default) for the publishes in flight. If you raise that value, raise `--stop-timeout` with it.

<Steps>

1. **Back up the store.**

2. **Recreate the container.**

   <Code code={upgradeCmd} lang="bash" />

3. **Check the log.**

   On start the broker upgrades the store when the new version needs it. Before it changes anything, it takes a
   checkpoint named `pre-upgrade-<from>-<to>` under `/data/backups` and keeps the three newest.

</Steps>

A store written by a newer version is refused: going back to an older image is not supported, restore a backup
taken with that version instead.

## Uninstall

```bash
docker rm -f tbmq-lite
docker volume rm tbmq-lite
```

The second command deletes all broker data.
