This guide covers deploying a TBMQ cluster on Azure Kubernetes Service (AKS) with the TBMQ Kubernetes scripts.

The scripts deploy two TBMQ broker nodes and two Integration Executors. TBMQ stores its data in Azure Database for
PostgreSQL and Azure Managed Redis, which you create with the `az` CLI, and in a Kafka cluster that runs in AKS. Web
traffic goes through an Azure Application Gateway, which the AKS ingress add-on configures from a Kubernetes Ingress,
and MQTT traffic through an Azure Load Balancer, created from a Kubernetes Service.

## Configure your Kubernetes environment

### Configure Azure tools

Sign in and select the subscription to deploy into:

```bash
az login
```

Register the resource providers this guide uses. A provider registers once per subscription; the command returns at
once for those that already are:

```bash
for ns in Microsoft.ContainerService Microsoft.Network Microsoft.DBforPostgreSQL Microsoft.Cache; do
  az provider register --namespace $ns --wait
done
```

### Define environment variables

The commands in this guide read these variables. Set them in the shell you run the guide from; if you open a new
shell, set them again:

```bash
export AKS_RESOURCE_GROUP=TBMQResources
export AKS_LOCATION=eastus
export AKS_GATEWAY=tbmq-gateway
export TB_CLUSTER_NAME=tbmq-cluster
export TB_DATABASE_NAME=tbmq-db
export TB_REDIS_NAME=tbmq-cache
echo "Resource group: $AKS_RESOURCE_GROUP, region: $AKS_LOCATION"
```

Where:

- `AKS_RESOURCE_GROUP`: the resource group that holds every resource of this guide.
- `AKS_LOCATION`: the Azure region. List the regions with `az account list-locations -o table`.
- `AKS_GATEWAY`: the name of the Application Gateway that the ingress add-on creates.
- `TB_CLUSTER_NAME`: the name of the AKS cluster.
- `TB_DATABASE_NAME` and `TB_REDIS_NAME`: the names of the PostgreSQL server and the Redis cache. Each is part of a
  public DNS name, so it must be unique across Azure: if a create command reports the name as taken, choose another,
  for example by adding your company name.

### Create the virtual network

Create the resource group:

```bash
az group create --name $AKS_RESOURCE_GROUP --location $AKS_LOCATION
```

Create a virtual network with a subnet for each part of the deployment: the AKS nodes and pods, the PostgreSQL server,
and the private endpoint of the Redis cache. The ingress add-on adds a fourth subnet, `10.10.16.0/24`, for the
Application Gateway when it creates the cluster:

```bash
az network vnet create --resource-group $AKS_RESOURCE_GROUP --name tbmq-vnet \
  --address-prefixes 10.10.0.0/16 \
  --subnet-name aks --subnet-prefixes 10.10.0.0/20

az network vnet subnet create --resource-group $AKS_RESOURCE_GROUP --vnet-name tbmq-vnet \
  --name postgres --address-prefixes 10.10.17.0/24 \
  --delegations Microsoft.DBforPostgreSQL/flexibleServers

az network vnet subnet create --resource-group $AKS_RESOURCE_GROUP --vnet-name tbmq-vnet \
  --name endpoints --address-prefixes 10.10.18.0/24
```

The PostgreSQL server and the Redis cache get private IP addresses in this network only, so they aren't reachable from
the internet.

### Create the AKS cluster

Create a cluster with three `Standard_D4s_v6` nodes, one in each availability zone of the region, and the
<a href="https://learn.microsoft.com/en-us/azure/application-gateway/ingress-controller-overview" target="_blank" rel="noopener noreferrer">Application Gateway ingress add-on</a>:

```bash
export AKS_SUBNET_ID=$(az network vnet subnet show --resource-group $AKS_RESOURCE_GROUP \
  --vnet-name tbmq-vnet --name aks --query id -o tsv)

az aks create --resource-group $AKS_RESOURCE_GROUP \
  --name $TB_CLUSTER_NAME \
  --vnet-subnet-id $AKS_SUBNET_ID \
  --network-plugin azure \
  --enable-addons ingress-appgw \
  --appgw-name $AKS_GATEWAY \
  --appgw-subnet-cidr 10.10.16.0/24 \
  --node-vm-size Standard_D4s_v6 \
  --node-count 3 \
  --zones 1 2 3
```

This takes about 10 minutes. `--network-plugin azure` gives each pod an IP address in the `aks` subnet, which the
Application Gateway routes to directly. To size the nodes for production, change `--node-vm-size` and `--node-count`;
see <a href="https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/overview" target="_blank" rel="noopener noreferrer">VM sizes</a>.
If the command fails with a quota error, the subscription's vCPU quota for the VM family or the region is too low:
<a href="https://learn.microsoft.com/en-us/azure/quotas/per-vm-quota-requests" target="_blank" rel="noopener noreferrer">request an increase</a>
or choose another region. If the region has no availability zones, drop `--zones`.

Add the cluster to your kubeconfig and switch the current context to it:

```bash
az aks get-credentials --resource-group $AKS_RESOURCE_GROUP --name $TB_CLUSTER_NAME
kubectl get nodes
```

<Aside type="caution" title="Check the kubectl context">
  Every command in this guide runs against your current kubectl context. If you switched it, switch back first. This
  command must print `tbmq-cluster`:

  ```bash
  kubectl config current-context
  ```
</Aside>

## Create the Azure managed services

Create the PostgreSQL server and the Redis cache in the virtual network. You can create them while the AKS cluster is
being created.

### Azure Database for PostgreSQL

The server resolves its name within the virtual network through a private DNS zone. Create the zone and link it to the
network:

```bash
az network private-dns zone create --resource-group $AKS_RESOURCE_GROUP \
  --name tbmq.private.postgres.database.azure.com

az network private-dns link vnet create --resource-group $AKS_RESOURCE_GROUP \
  --zone-name tbmq.private.postgres.database.azure.com --name tbmq-postgres-dns-link \
  --virtual-network tbmq-vnet --registration-enabled false
```

Create a PostgreSQL 17 flexible server in the `postgres` subnet, highly available with a standby server in another
availability zone. Replace `YOUR_DB_PASSWORD` with a strong password of 8 to 128 characters that mixes upper and lower
case letters, digits, and symbols other than quotes and backslashes; you need it to
[connect TBMQ](#connect-to-postgresql):

```bash
az postgres flexible-server create --resource-group $AKS_RESOURCE_GROUP \
  --name $TB_DATABASE_NAME \
  --location $AKS_LOCATION \
  --version 17 \
  --tier GeneralPurpose --sku-name Standard_D2ds_v5 \
  --storage-size 32 \
  --zonal-resiliency Enabled \
  --vnet tbmq-vnet --subnet postgres \
  --private-dns-zone tbmq.private.postgres.database.azure.com \
  --admin-user tbmqadmin --admin-password 'YOUR_DB_PASSWORD' \
  --yes
```

The server takes about 10 minutes to create. Recommendations:

- **High availability**: `--zonal-resiliency Enabled` keeps a standby server in another zone. If the command fails
  with `This location has a single availability zone`, the region doesn't offer zone-redundant high availability to
  your subscription: add `--allow-same-zone` to keep the standby in the same zone. For development,
  `--zonal-resiliency Disabled` runs a single server at half the cost.
- **Size**: give production at least 2 vCores (`Standard_D2ds_v5`); see
  <a href="https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-compute" target="_blank" rel="noopener noreferrer">Compute options</a>.
- **Network**: the server gets an address in the `postgres` subnet only. If the command fails with
  `PrivateDnsZoneNameNotValid`, the private DNS zone doesn't exist yet: create it as shown above.

Create the database TBMQ connects to:

```bash
az postgres flexible-server db create --resource-group $AKS_RESOURCE_GROUP \
  --server-name $TB_DATABASE_NAME --name thingsboard_mqtt_broker
```

### Azure Managed Redis

TBMQ uses a Redis-compatible cache to store messages for
<DocLink product={props.product} path="architecture/#persistent-device-client">DEVICE persistent clients</DocLink>
and to cache MQTT client credentials. Without the cache, every new connection queries the database to validate its
credentials, which can overload the database under high connection rates.

<a href="https://learn.microsoft.com/en-us/azure/redis/overview" target="_blank" rel="noopener noreferrer">Azure Managed Redis</a>
runs Redis 7.4, compatible with the Valkey 8 that TBMQ supports. Create a cache with access-key authentication and no
public network access:

```bash
az redisenterprise create --resource-group $AKS_RESOURCE_GROUP \
  --name $TB_REDIS_NAME \
  --location $AKS_LOCATION \
  --sku Balanced_B1 \
  --clustering-policy EnterpriseCluster \
  --client-protocol Encrypted \
  --access-keys-authentication Enabled \
  --public-network-access Disabled
```

The cache takes about 10 minutes to create. Recommendations:

- **Size**: `Balanced_B1` (1 GB) to start. DEVICE persistent clients keep their undelivered messages in the cache, so
  size it for them; see
  <a href="https://learn.microsoft.com/en-us/azure/redis/overview#choosing-the-right-tier" target="_blank" rel="noopener noreferrer">Choosing the right tier</a>.
- **Clustering policy**: `EnterpriseCluster` serves every shard through one endpoint, which TBMQ uses as a standalone
  connection.
- **TLS**: clients connect over TLS on port `10000`.
- **High availability**: on by default, with a replica of each shard.

The cache reaches the virtual network through a
<a href="https://learn.microsoft.com/en-us/azure/redis/private-link" target="_blank" rel="noopener noreferrer">private endpoint</a>
in the `endpoints` subnet. Create the endpoint and a private DNS zone that resolves the cache's name to it:

```bash
az network private-dns zone create --resource-group $AKS_RESOURCE_GROUP \
  --name privatelink.redis.azure.net

az network private-dns link vnet create --resource-group $AKS_RESOURCE_GROUP \
  --zone-name privatelink.redis.azure.net --name tbmq-redis-dns-link \
  --virtual-network tbmq-vnet --registration-enabled false

az network private-endpoint create --resource-group $AKS_RESOURCE_GROUP \
  --name tbmq-redis-endpoint \
  --vnet-name tbmq-vnet --subnet endpoints \
  --private-connection-resource-id $(az redisenterprise show --resource-group $AKS_RESOURCE_GROUP \
    --name $TB_REDIS_NAME --query id -o tsv) \
  --group-id redisEnterprise \
  --connection-name tbmq-redis-connection

az network private-endpoint dns-zone-group create --resource-group $AKS_RESOURCE_GROUP \
  --endpoint-name tbmq-redis-endpoint --name default \
  --private-dns-zone privatelink.redis.azure.net --zone-name redis
```

## Connect TBMQ to the managed services

### Connect to PostgreSQL

Get the host name of the server:

```bash
az postgres flexible-server show --resource-group $AKS_RESOURCE_GROUP --name $TB_DATABASE_NAME \
  --query fullyQualifiedDomainName -o tsv
```

In `tbmq-db-configmap.yml`, replace `YOUR_AZURE_POSTGRES_ENDPOINT_URL` with it, `YOUR_AZURE_POSTGRES_USER` with
`tbmqadmin`, and `YOUR_AZURE_POSTGRES_PASSWORD` with the password you set:

```yaml
  SPRING_DATASOURCE_URL: "jdbc:postgresql://tbmq-db.postgres.database.azure.com/thingsboard_mqtt_broker?sslmode=require"
  SPRING_DATASOURCE_USERNAME: "tbmqadmin"
  SPRING_DATASOURCE_PASSWORD: "secret"
```

### Connect to Azure Managed Redis

Once the cache is **Running**, get its host name and access key:

```bash
az redisenterprise show --resource-group $AKS_RESOURCE_GROUP --name $TB_REDIS_NAME \
  --query hostName -o tsv
az redisenterprise database list-keys --resource-group $AKS_RESOURCE_GROUP \
  --cluster-name $TB_REDIS_NAME --query primaryKey -o tsv
```

In `tbmq-cache-configmap.yml`, replace `YOUR_REDIS_HOST_NAME` with the host name and `YOUR_REDIS_ACCESS_KEY` with the
key:

```yaml
  REDIS_CONNECTION_TYPE: "standalone"
  REDIS_HOST: "tbmq-cache.eastus.redis.azure.net"
  REDIS_PORT: "10000"
  REDIS_PASSWORD: "YOUR_REDIS_ACCESS_KEY"
  REDIS_SSL_ENABLED: "true"
  REDIS_SSL_CERT_FILE: "/etc/ssl/certs/ca-certificates.crt"
```

TBMQ verifies the cache's TLS certificate against the CA certificates of its container image, which include the roots
that Azure certificates chain to.

## Deploy Kafka

Kafka runs in the AKS cluster. Deploy it with one of these options, and in both `tbmq.yml` and `tbmq-ie.yml`
uncomment the matching `TB_KAFKA_SERVERS` block.

<Aside title="Why not Azure Event Hubs">
  Azure Event Hubs serves the Kafka protocol, but each event hub is one topic, and a namespace holds at most 10 on the
  Standard tier and 100 per processing unit on Premium. TBMQ needs at least 30 topics and creates another for each
  persistent APPLICATION client, so it quickly outgrows a namespace.
</Aside>

### Option 1. Apache Kafka StatefulSet

Three pods in KRaft dual-role mode: each node is both a controller and a broker. See the
<a href={props.product === Products.TBMQ_PE ? kafkaPeReadmeUrl : kafkaCeReadmeUrl} target="_blank" rel="noopener noreferrer">full deployment guide</a>.

```bash
kubectl apply -f kafka/tbmq-kafka.yml
kubectl rollout status statefulset/tbmq-kafka --timeout=300s
```

Uncomment the block marked `Uncomment the following lines to connect to Apache Kafka`.

### Option 2. Strimzi operator

The Strimzi Cluster Operator manages upgrades and scaling. See the
<a href={props.product === Products.TBMQ_PE ? kafkaPeOperatorReadmeUrl : kafkaCeOperatorReadmeUrl} target="_blank" rel="noopener noreferrer">full deployment guide</a>.

```bash
helm install tbmq-kafka -f kafka/operator/values-strimzi-kafka-operator.yaml oci://quay.io/strimzi-helm/strimzi-kafka-operator --version 0.47.0
kubectl apply -f kafka/operator/kafka-cluster.yaml
kubectl wait kafka/tbmq --for=condition=Ready --timeout=300s
```

Uncomment the block marked `Uncomment the following lines to connect to Strimzi`.

## Configure load balancers

The `receipts` directory holds one manifest per load balancer. Apply one HTTP manifest and the MQTT manifest:

| Manifest                  | Load balancer        | Ports                                                                                 |
|---------------------------|----------------------|---------------------------------------------------------------------------------------|
| `http-load-balancer.yml`  | Application Gateway  | `80` (HTTP)                                                                           |
| `https-load-balancer.yml` | Application Gateway  | `443` (HTTPS); `80` redirects to HTTPS                                                |
| `mqtt-load-balancer.yml`  | Azure Load Balancer  | `1883` (MQTT), `8084` (MQTT over WebSockets); `8883` and `8085` passed through to TBMQ |

### HTTP load balancer

<Aside>Suitable for development only. For production, use the [HTTPS load balancer](#https-load-balancer) instead.</Aside>

```bash
kubectl apply -f receipts/http-load-balancer.yml
```

### HTTPS load balancer

The Application Gateway terminates HTTPS with a certificate that you upload to it. Prepare the certificate of your
domain and its private key as a password-protected PFX file, then add it to the gateway as `TBMQHTTPSCert`, the name
the manifest refers to. The ingress add-on creates the gateway in the cluster's node resource group:

```bash
az network application-gateway ssl-cert create \
  --resource-group $(az aks show --resource-group $AKS_RESOURCE_GROUP --name $TB_CLUSTER_NAME \
    --query nodeResourceGroup -o tsv) \
  --gateway-name $AKS_GATEWAY \
  --name TBMQHTTPSCert \
  --cert-file YOUR_CERT.pfx \
  --cert-password YOUR_CERT_PASSWORD
```

Both manifests configure the same Application Gateway, so apply only one. If you applied the HTTP manifest, delete it,
then apply the HTTPS one:

```bash
kubectl delete -f receipts/http-load-balancer.yml --ignore-not-found
kubectl apply -f receipts/https-load-balancer.yml
```

Point your domain at the gateway's address, shown in [Validate HTTP access](#validate-http-access), with a DNS `A`
record.

### MQTT load balancer

```bash
kubectl apply -f receipts/mqtt-load-balancer.yml
```

The Azure Load Balancer passes TCP through to TBMQ unchanged, so it can't terminate TLS. It serves plain MQTT on
`1883` and `8084`, and forwards `8883` and `8085` to TBMQ, which serves them once you enable
[MQTT over TLS](#mqtt-over-tls).

### MQTT over TLS

TBMQ terminates TLS itself on `8883` (MQTTS) and `8085` (MQTT over secure WebSockets). This also supports
<DocLink product={props.product} path="security/authentication/x509" bold={false}>X.509 certificate authentication</DocLink>.

Prepare the server certificate chain and its private key in PEM format; see
<DocLink product={props.product} path="security/mqtts" bold={false}>MQTT over SSL</DocLink>. Create a ConfigMap from
them. The same command replaces the files when you renew the certificate:

```bash
kubectl create configmap tbmq-mqtts-config -n thingsboard-mqtt-broker \
  --from-file=server.pem=YOUR_PEM_FILENAME \
  --from-file=mqttserver_key.pem=YOUR_PEM_KEY_FILENAME \
  -o yaml --dry-run=client | kubectl apply -f -
```

Where:

- `YOUR_PEM_FILENAME`: the server certificate chain file.
- `YOUR_PEM_KEY_FILENAME`: the server certificate's private key file.

In `tbmq.yml`, uncomment the three blocks marked `Uncomment the following lines to enable two-way MQTTS`. They mount
the certificate and enable MQTTS on `8883` and MQTT over secure WebSockets on `8085`. Apply the updated `tbmq.yml`,
which restarts the broker nodes one at a time:

```bash
kubectl apply -f tbmq.yml
```

```text
tbmq-mqtt-loadbalancer   LoadBalancer   10.0.183.214   20.76.143.18    1883:31215/TCP,8084:30447/TCP,8883:32014/TCP,8085:31871/TCP   2m
```

MQTT clients connect to the `EXTERNAL-IP` on the ports listed in [Configure load balancers](#configure-load-balancers).

To check the broker end to end, publish and subscribe with the
<a href="https://mosquitto.org/download/" target="_blank" rel="noopener noreferrer">Mosquitto clients</a>. A new
installation has one MQTT credential, **TBMQ WebSockets MQTT Credentials**: username `tbmq_websockets_username` and no
password. In one terminal, subscribe:

```bash
mosquitto_sub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/#' -v -q 1
```

In another, publish:

```bash
mosquitto_pub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/hello' -m 'hello from aks' -q 1
```

The subscriber prints `tbmq/demo/hello hello from aks`. A client that connects without a username is refused as not
authorized, because MQTT Basic authentication is enabled by default. To create your own credentials, see
<DocLink product={props.product} path="user-guide/ui/mqtt-client-credentials" bold={false}>MQTT client credentials</DocLink>.

## Troubleshooting

View the logs of a broker node:

```bash
kubectl logs -f tbmq-0 -n thingsboard-mqtt-broker
```

Check the state of the StatefulSets:

```bash
kubectl get statefulsets -n thingsboard-mqtt-broker
```

If a broker node logs connection errors to PostgreSQL or Redis, check the host name you set, and that the server's
private DNS zone and the `privatelink.redis.azure.net` zone are linked to `tbmq-vnet`. Redis authentication errors mean
the access key in `tbmq-cache-configmap.yml` is wrong.

If the Ingress `ADDRESS` or the Service `EXTERNAL-IP` stays empty, its events give the reason. The ingress add-on logs
how it configures the Application Gateway:

```bash
kubectl describe ingress -n thingsboard-mqtt-broker
kubectl describe svc tbmq-mqtt-loadbalancer -n thingsboard-mqtt-broker
kubectl logs deployment/ingress-appgw-deployment -n kube-system
```

See the <a href="https://kubernetes.io/docs/reference/kubectl/cheatsheet/" target="_blank" rel="noopener noreferrer">kubectl Cheat Sheet</a> for more details.

The upgrade merges the new release branch into your clone and keeps your settings. Git merges only committed changes,
so commit your settings first:

```bash
git add -A .
git commit -m "TBMQ configuration"
```

If Git asks who you are, set `git config user.name` and `git config user.email`, then commit again.

If the merge reports conflicts, list the conflicting files:

```bash
git diff --name-only --diff-filter=U
```

If you didn't change any of them, for example the `pom.xml` files of the TBMQ source code, take the release's version

<Aside type="caution">
  Both commands are required. `k8s-upgrade-tbmq.sh` upgrades the database but does not touch the TBMQ pods — they keep

  MQTT clients can't connect from the first command until the new pods are ready.
</Aside>

## Cluster deletion

To remove TBMQ but keep the AKS cluster and the managed services, run the first three steps. To remove everything this
guide created, run the last step alone.

<Steps>

1. **Delete the TBMQ nodes.**

   ```bash
   ./k8s-delete-tbmq.sh
   ```

2. **Delete Kafka, if it runs with Strimzi.** Delete the Kafka cluster first, then the operator:

   ```bash
   kubectl delete -f kafka/operator/kafka-cluster.yaml
   helm uninstall tbmq-kafka
   ```

3. **Delete the remaining resources in the `thingsboard-mqtt-broker` namespace**: the Services, including the MQTT load
   balancer, the StatefulSets, including the Kafka StatefulSet, the ConfigMaps, the Ingress, and the persistent volume
   claims:

   ```bash
   ./k8s-delete-all.sh
   ```

4. **Delete the resource group.** This deletes everything in it: the AKS cluster with its node resource group and
   Application Gateway, the PostgreSQL server, the Redis cache, the private endpoint, the private DNS zones, and the
   virtual network. It takes about 15 minutes:

   ```bash
   az group delete --name $AKS_RESOURCE_GROUP
   ```

</Steps>
