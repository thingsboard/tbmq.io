This guide covers deploying a TBMQ cluster on Google Kubernetes Engine (GKE) with the TBMQ Kubernetes scripts.

The scripts deploy two TBMQ broker nodes and two Integration Executors. TBMQ stores its data in Cloud SQL for
PostgreSQL, Google Cloud Managed Service for Apache Kafka, and Memorystore for Valkey, which you create with the
`gcloud` CLI. Web traffic goes through a Google Cloud Application Load Balancer, created from a GKE Ingress, and MQTT
traffic through a passthrough Network Load Balancer, created from a Kubernetes Service.

## Configure your Kubernetes environment

### Configure GCP tools

Create a Google Cloud project (recommended) or choose an existing one, then sign in and select it:

```bash
gcloud init
```

Enable the APIs this guide uses:

```bash
gcloud services enable container.googleapis.com \
  sqladmin.googleapis.com servicenetworking.googleapis.com \
  managedkafka.googleapis.com memorystore.googleapis.com \
  networkconnectivity.googleapis.com
```

### Define environment variables

The commands in this guide read these variables. Set them in the shell you run the guide from; if you open a new
shell, set them again:

```bash
export GCP_PROJECT=$(gcloud config get-value project)
export GCP_REGION=us-central1
export GCP_ZONE1=us-central1-a
export GCP_ZONE2=us-central1-b
export GCP_ZONE3=us-central1-c
export GCP_NETWORK=default
export TB_CLUSTER_NAME=tbmq-cluster
export TB_DATABASE_NAME=tbmq-db
export TB_KAFKA_NAME=tbmq-kafka
export TB_VALKEY_NAME=tbmq-valkey
echo "Project: $GCP_PROJECT, region: $GCP_REGION, network: $GCP_NETWORK"
echo "Zones: $GCP_ZONE1,$GCP_ZONE2,$GCP_ZONE3"
```

Where:

- `GCP_PROJECT`: the project selected in your `gcloud` configuration.
- `GCP_REGION` and `GCP_ZONE1`–`GCP_ZONE3`: a
  <a href="https://docs.cloud.google.com/compute/docs/regions-zones#available" target="_blank" rel="noopener noreferrer">compute region</a>
  and three of its zones. Every resource in this guide is created in this region.
- `GCP_NETWORK`: the VPC network, `default` for the network every new project has. Its subnet in each region is also
  named `default`; if you use another network, the commands below that name the subnet use `$GCP_NETWORK` too, so
  give the subnet the same name or edit those commands.
- `TB_CLUSTER_NAME`, `TB_DATABASE_NAME`, `TB_KAFKA_NAME`, `TB_VALKEY_NAME`: the names of the GKE cluster, the Cloud
  SQL instance, the Kafka cluster, and the Valkey instance.

### Create the GKE cluster

Create a regional cluster with one `e2-standard-4` node in each of the three zones. To size the nodes for production,
change `--machine-type` and `--num-nodes`; see
<a href="https://docs.cloud.google.com/compute/docs/machine-resource" target="_blank" rel="noopener noreferrer">machine families</a>.

```bash
gcloud container clusters create $TB_CLUSTER_NAME \
  --release-channel stable \
  --region $GCP_REGION \
  --network=$GCP_NETWORK \
  --node-locations $GCP_ZONE1,$GCP_ZONE2,$GCP_ZONE3 \
  --enable-ip-alias \
  --num-nodes=1 \
  --node-labels=role=main \
  --machine-type=e2-standard-4
```

This takes about 10 minutes. When it finishes, `gcloud` adds the cluster to your kubeconfig and switches the current
context to it. To get the credentials again later, for example on another machine:

```bash
gcloud container clusters get-credentials $TB_CLUSTER_NAME --region $GCP_REGION
```

<Aside type="caution" title="Check the kubectl context">
  Every command in this guide runs against your current kubectl context. If you switched it, switch back first. This
  command must print `gke_{project}_{region}_tbmq-cluster`:

  ```bash
  kubectl config current-context
  ```
</Aside>

## Create the Google Cloud managed services

Create the PostgreSQL database, the Kafka cluster, and the Valkey cache in the cluster's region and VPC network. They
get private IP addresses only, which the GKE nodes reach without further firewall rules. You can create them in
parallel; the Kafka cluster takes the longest, about 30 minutes.

### Cloud SQL for PostgreSQL

Cloud SQL reaches your VPC network through
<a href="https://docs.cloud.google.com/vpc/docs/private-services-access" target="_blank" rel="noopener noreferrer">private services access</a>,
which each network needs once. Check whether the network already has it:

```bash
gcloud services vpc-peerings list --network=$GCP_NETWORK
```

If the output lists the `servicenetworking-googleapis-com` peering, skip to the instance. Otherwise, reserve an IP range
for Google services and connect it to the network:

```bash
gcloud compute addresses create google-managed-services-$GCP_NETWORK \
  --global \
  --purpose=VPC_PEERING \
  --prefix-length=16 \
  --network=projects/$GCP_PROJECT/global/networks/$GCP_NETWORK

gcloud services vpc-peerings connect \
  --service=servicenetworking.googleapis.com \
  --ranges=google-managed-services-$GCP_NETWORK \
  --network=$GCP_NETWORK
```

Create a PostgreSQL 17 instance with a private IP address only, highly available across two zones of the region:

```bash
gcloud sql instances create $TB_DATABASE_NAME \
  --database-version=POSTGRES_17 \
  --region=$GCP_REGION --availability-type=regional \
  --no-assign-ip --network=projects/$GCP_PROJECT/global/networks/$GCP_NETWORK \
  --cpu=2 --memory=7680MB --edition=ENTERPRISE
```

For development, `--availability-type=zonal` runs a single instance at half the cost. Give production at least 2 vCPUs
and 7.5 GB of memory. For every option, see
<a href="https://docs.cloud.google.com/sql/docs/postgres/create-instance" target="_blank" rel="noopener noreferrer">Create instances</a>.

Set the password of the `postgres` user. Replace `secret` with a strong password; you need it to
[connect TBMQ](#connect-to-cloud-sql):

```bash
gcloud sql users set-password postgres \
  --instance=$TB_DATABASE_NAME \
  --password=secret
```

Create the database TBMQ connects to:

```bash
gcloud sql databases create thingsboard_mqtt_broker --instance=$TB_DATABASE_NAME
```

### Managed Service for Apache Kafka

Create a Kafka cluster with 3 vCPUs and 3 GiB of memory, the smallest size the service offers. Its brokers get
addresses in the region's subnet of your network:

```bash
gcloud managed-kafka clusters create $TB_KAFKA_NAME \
  --location=$GCP_REGION \
  --cpu=3 \
  --memory=3GiB \
  --subnets=projects/$GCP_PROJECT/regions/$GCP_REGION/subnetworks/$GCP_NETWORK \
  --async
```

`--async` returns at once; the cluster takes about 30 minutes to create. To size it for production, see
<a href="https://docs.cloud.google.com/managed-service-for-apache-kafka/docs/plan-cluster-size" target="_blank" rel="noopener noreferrer">Plan your Kafka cluster size</a>.

The cluster accepts only authenticated TLS connections. TBMQ signs in with a service account key over SASL/PLAIN.
Create a service account, allow it to use Kafka, and create a key for it. Keep the key file outside the cloned
repository, so Git never picks it up:

```bash
gcloud iam service-accounts create tbmq-kafka-client --display-name="TBMQ Kafka client"

gcloud projects add-iam-policy-binding $GCP_PROJECT \
  --member=serviceAccount:tbmq-kafka-client@$GCP_PROJECT.iam.gserviceaccount.com \
  --role=roles/managedkafka.client --condition=None

gcloud iam service-accounts keys create ~/tbmq-kafka-client-key.json \
  --iam-account=tbmq-kafka-client@$GCP_PROJECT.iam.gserviceaccount.com
```

<Aside>
  If your organization blocks service account key creation (the `iam.disableServiceAccountKeyCreation` policy), the
  last command fails. Ask an administrator to exempt the project, or [run Kafka in the cluster](#run-kafka-in-the-cluster)
  instead.
</Aside>

### Memorystore for Valkey

TBMQ uses Valkey to store messages for
<DocLink product={props.product} path="architecture/#persistent-device-client">DEVICE persistent clients</DocLink>
and to cache MQTT client credentials. Without the cache, every new connection queries the database to validate its
credentials, which can overload the database under high connection rates.

Memorystore reaches your network through
<a href="https://docs.cloud.google.com/memorystore/docs/valkey/networking" target="_blank" rel="noopener noreferrer">Private Service Connect</a>,
which needs a service connection policy for the network and region. Check whether one exists:

```bash
gcloud network-connectivity service-connection-policies list --region=$GCP_REGION \
  --filter="serviceClass=gcp-memorystore"
```

If none is listed, create it:

```bash
gcloud network-connectivity service-connection-policies create tbmq-valkey-policy \
  --network=$GCP_NETWORK \
  --region=$GCP_REGION \
  --service-class=gcp-memorystore \
  --subnets=https://www.googleapis.com/compute/v1/projects/$GCP_PROJECT/regions/$GCP_REGION/subnetworks/$GCP_NETWORK
```

Create a Valkey 8.0 instance with cluster mode enabled, one shard, and one replica in another zone:

```bash
gcloud memorystore instances create $TB_VALKEY_NAME \
  --location=$GCP_REGION \
  --psc-auto-connections=network=projects/$GCP_PROJECT/global/networks/$GCP_NETWORK,projectId=$GCP_PROJECT \
  --mode=cluster \
  --shard-count=1 \
  --replica-count=1 \
  --node-type=standard-small \
  --engine-version=VALKEY_8_0 \
  --async
```

The instance takes about 15 minutes to create. Recommendations:

- **Cluster mode**: enabled (`--mode=cluster`) for production, which this guide uses. With `--mode=cluster-disabled`,
  a single primary node serves every key, with optional replicas; TBMQ supports both.
- **Shards**: for production, 3 shards (`--shard-count=3`) with 1 replica each.
- **Node type**: `standard-small` (6.5 GB) to start; see
  <a href="https://docs.cloud.google.com/memorystore/docs/valkey/instance-node-specification" target="_blank" rel="noopener noreferrer">Instance and node specification</a>.
- **Encryption in transit and authentication**: both off by default, which this guide uses. TBMQ connects without TLS
  and without a password unless you configure it to.

## Connect TBMQ to the managed services

### Connect to Cloud SQL

Once the instance is **RUNNABLE**, get its private IP address:

```bash
gcloud sql instances describe $TB_DATABASE_NAME --format="value(ipAddresses[0].ipAddress)"
```

In `tbmq-db-configmap.yml`, replace `YOUR_DB_IP_ADDRESS` with it, `YOUR_DB_NAME` with `thingsboard_mqtt_broker`, and
`YOUR_DB_PASSWORD` with the password you set:

```yaml
  SPRING_DATASOURCE_URL: "jdbc:postgresql://172.16.0.2:5432/thingsboard_mqtt_broker"
  SPRING_DATASOURCE_USERNAME: "postgres"
  SPRING_DATASOURCE_PASSWORD: "secret"
```

### Connect to Managed Kafka

Once the cluster is **ACTIVE**, get its bootstrap address:

```bash
gcloud managed-kafka clusters describe $TB_KAFKA_NAME --location=$GCP_REGION --format="value(bootstrapAddress)"
```

In both `tbmq.yml` and `tbmq-ie.yml`, uncomment the block marked
`Uncomment the following lines to connect to Google Cloud Managed Service for Apache Kafka` and replace
`PUT_YOUR_KAFKA_BOOTSTRAP_ADDRESS_HERE` with the address:

```yaml
            - name: TB_KAFKA_SERVERS
              value: "bootstrap-xxxxxxxxxx.xxxxxxxxx.us-central1.managedkafka.s.cloud.goog:9092"
            - name: TB_KAFKA_DEFAULT_PRODUCER_CONSUMER_CONFIG
              valueFrom:
                secretKeyRef:
                  name: tbmq-kafka-credentials
                  key: kafka-config
```

`TB_KAFKA_DEFAULT_PRODUCER_CONSUMER_CONFIG` carries the SASL settings and the service account key, from the
`tbmq-kafka-credentials` Secret that you create after [installing the database schema](#install-the-database-schema).

### Connect to Memorystore

Once the instance is **ACTIVE**, list its endpoints:

```bash
gcloud memorystore instances describe $TB_VALKEY_NAME --location=$GCP_REGION \
  --flatten="endpoints[].connections[]" \
  --format="table(endpoints.connections.pscAutoConnection.connectionType:label=TYPE,endpoints.connections.pscAutoConnection.ipAddress:label=ADDRESS)"
```

```text
TYPE                       ADDRESS
CONNECTION_TYPE_DISCOVERY  10.128.0.36
                           10.128.0.35
```

TBMQ connects to the `CONNECTION_TYPE_DISCOVERY` address; the other one is used by Memorystore internally. In
`tbmq-cache-configmap.yml`, set it with port `6379` in `REDIS_NODES`, and keep `REDIS_CONNECTION_TYPE: "cluster"`:

```yaml
  REDIS_CONNECTION_TYPE: "cluster"
  REDIS_NODES: "10.128.0.36:6379"
```

With cluster mode disabled, the command lists a `CONNECTION_TYPE_PRIMARY` address instead. Set it, without the port,
in `REDIS_HOST`, and set the connection type to `standalone`:

```yaml
  REDIS_CONNECTION_TYPE: "standalone"
  REDIS_HOST: "10.128.0.36"
```

## Configure load balancers

The `receipts` directory holds one manifest per load balancer. Apply one HTTP manifest and the MQTT manifest:

| Manifest                  | Load balancer                    | Ports                                                                                 |
|---------------------------|----------------------------------|---------------------------------------------------------------------------------------|
| `http-load-balancer.yml`  | Application Load Balancer        | `80` (HTTP)                                                                           |
| `https-load-balancer.yml` | Application Load Balancer        | `443` (HTTPS); `80` redirects to HTTPS                                                |
| `mqtt-load-balancer.yml`  | Passthrough Network Load Balancer | `1883` (MQTT), `8084` (MQTT over WebSockets); `8883` and `8085` passed through to TBMQ |

### HTTP load balancer

<Aside>Suitable for development only. For production, use the [HTTPS load balancer](#https-load-balancer) instead.</Aside>

```bash
kubectl apply -f receipts/http-load-balancer.yml
```

### HTTPS load balancer

The Application Load Balancer serves HTTPS with a
<a href="https://docs.cloud.google.com/kubernetes-engine/docs/how-to/managed-certs" target="_blank" rel="noopener noreferrer">Google-managed certificate</a>
for your domain. Reserve a global static IP address, which the manifest names `tbmq-http-lb-address`, and print it:

```bash
gcloud compute addresses create tbmq-http-lb-address --global
gcloud compute addresses describe tbmq-http-lb-address --global --format="value(address)"
```

Point your domain at the address with a DNS `A` record. In `receipts/https-load-balancer.yml`, replace
`PUT_YOUR_DOMAIN_HERE` with the domain, then apply the manifest:

```bash
kubectl apply -f receipts/https-load-balancer.yml
```

The certificate is issued once the domain resolves to the address, which can take up to 60 minutes. Its status turns
`Active`:

```bash
kubectl describe managedcertificate managed-cert -n thingsboard-mqtt-broker
```

### MQTT load balancer

```bash
kubectl apply -f receipts/mqtt-load-balancer.yml
```

The Network Load Balancer passes TCP through to TBMQ unchanged, so it can't terminate TLS. It serves plain MQTT on
`1883` and `8084`, and forwards `8883` and `8085` to TBMQ, which serves them once you enable
[MQTT over TLS](#mqtt-over-tls).

### MQTT over TLS

TBMQ terminates TLS itself on `8883` (MQTTS) and `8085` (MQTT over secure WebSockets). This also supports
<DocLink product={props.product} path="security/authentication/x509" bold={false}>X.509 certificate authentication</DocLink>.

Prepare the server certificate chain and its private key in PEM format; see
<DocLink product={props.product} path="security/mqtts" bold={false}>MQTT over SSL</DocLink>. Create a ConfigMap from
them. The same command replaces the files when you renew the certificate:

```bash
kubectl create configmap tbmq-mqtts-config -n thingsboard-mqtt-broker \
  --from-file=server.pem=YOUR_PEM_FILENAME \
  --from-file=mqttserver_key.pem=YOUR_PEM_KEY_FILENAME \
  -o yaml --dry-run=client | kubectl apply -f -
```

Where:

- `YOUR_PEM_FILENAME`: the server certificate chain file.
- `YOUR_PEM_KEY_FILENAME`: the server certificate's private key file.

In `tbmq.yml`, uncomment the three blocks marked `Uncomment the following lines to enable two-way MQTTS`. They mount
the certificate and enable MQTTS on `8883` and MQTT over secure WebSockets on `8085`. Apply the updated `tbmq.yml`,
which restarts the broker nodes one at a time:

```bash
kubectl apply -f tbmq.yml
```

## Validate HTTP access

Get the address of the Application Load Balancer:

```bash
kubectl get ingress -n thingsboard-mqtt-broker
```

```text
NAME                     CLASS    HOSTS   ADDRESS         PORTS   AGE
tbmq-http-loadbalancer   <none>   *       136.82.226.40   80      7m
```

health checks pass. Then open `http://{ADDRESS}` in your browser, or your domain over HTTPS if you deployed the HTTPS
load balancer, and sign in as System Administrator:

```text title="Username"
sysadmin@thingsboard.org
```

```text title="Password"
sysadmin
```

## Validate MQTT access

Get the address of the Network Load Balancer:

```bash
kubectl get svc tbmq-mqtt-loadbalancer -n thingsboard-mqtt-broker
```

```text
NAME                     TYPE           CLUSTER-IP       EXTERNAL-IP      PORT(S)                                                       AGE
tbmq-mqtt-loadbalancer   LoadBalancer   34.118.227.221   104.198.132.85   1883:32086/TCP,8084:32211/TCP,8883:30408/TCP,8085:32092/TCP   3m
```

MQTT clients connect to the `EXTERNAL-IP` on the ports listed in [Configure load balancers](#configure-load-balancers).

To check the broker end to end, publish and subscribe with the
<a href="https://mosquitto.org/download/" target="_blank" rel="noopener noreferrer">Mosquitto clients</a>. A new
installation has one MQTT credential, **TBMQ WebSockets MQTT Credentials**: username `tbmq_websockets_username` and no
password. In one terminal, subscribe:

```bash
mosquitto_sub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/#' -v -q 1
```

In another, publish:

```bash
mosquitto_pub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/hello' -m 'hello from gke' -q 1
```

The subscriber prints `tbmq/demo/hello hello from gke`. A client that connects without a username is refused as not
authorized, because MQTT Basic authentication is enabled by default. To create your own credentials, see
<DocLink product={props.product} path="user-guide/ui/mqtt-client-credentials" bold={false}>MQTT client credentials</DocLink>.

## Troubleshooting

View the logs of a broker node:

```bash
kubectl logs -f tbmq-0 -n thingsboard-mqtt-broker
```

Check the state of the StatefulSets:

```bash
kubectl get statefulsets -n thingsboard-mqtt-broker
```

If a broker node logs connection errors to PostgreSQL, Kafka, or Valkey, check the address you set, and that the
service is in the same region and VPC network as the GKE cluster. Kafka authentication errors mean the
`tbmq-kafka-credentials` Secret or the service account's `roles/managedkafka.client` role is wrong.

If the Ingress `ADDRESS` or the Service `EXTERNAL-IP` stays empty, its events give the reason:

```bash
kubectl describe ingress -n thingsboard-mqtt-broker
kubectl describe svc tbmq-mqtt-loadbalancer -n thingsboard-mqtt-broker
```

See the <a href="https://kubernetes.io/docs/reference/kubectl/cheatsheet/" target="_blank" rel="noopener noreferrer">kubectl Cheat Sheet</a> for more details.

```bash

```

## Cluster deletion

<Steps>

1. **Delete the TBMQ nodes.**

   ```bash
   ./k8s-delete-tbmq.sh
   ```

2. **Delete Kafka, if it runs in the cluster with Strimzi.** Delete the Kafka cluster first, then the operator:

   ```bash
   kubectl delete -f kafka/operator/kafka-cluster.yaml
   helm uninstall tbmq-kafka
   ```

3. **Delete the HTTPS load balancer, if you deployed it.** `k8s-delete-all.sh` doesn't delete its
   `ManagedCertificate`, and GKE deletes the Google-managed SSL certificate only when that object is deleted:

   ```bash
   kubectl delete -f receipts/https-load-balancer.yml
   ```

4. **Delete the remaining resources in the `thingsboard-mqtt-broker` namespace**: the Services, including the MQTT load
   balancer, the StatefulSets, the ConfigMaps, the Ingress, and the persistent volume claims:

   ```bash
   ./k8s-delete-all.sh
   ```

5. **Wait for the load balancers to go.** GKE deletes them once the Ingress and the Service are gone. Wait until this
   command lists nothing:

   ```bash
   gcloud compute forwarding-rules list --filter="description~thingsboard-mqtt-broker" --format="table(name,IPAddress)"
   ```

6. **Delete the GKE cluster.**

   ```bash
   gcloud container clusters delete $TB_CLUSTER_NAME --region=$GCP_REGION
   ```

7. **Delete the managed services.**

   ```bash
   gcloud sql instances delete $TB_DATABASE_NAME
   gcloud managed-kafka clusters delete $TB_KAFKA_NAME --location=$GCP_REGION
   gcloud memorystore instances delete $TB_VALKEY_NAME --location=$GCP_REGION
   ```

8. **Delete the Kafka service account and its role binding.** Deleting the service account also deletes its key; delete
   the local key file too:

   ```bash
   gcloud projects remove-iam-policy-binding $GCP_PROJECT \
     --member=serviceAccount:tbmq-kafka-client@$GCP_PROJECT.iam.gserviceaccount.com \
     --role=roles/managedkafka.client --condition=None
   gcloud iam service-accounts delete tbmq-kafka-client@$GCP_PROJECT.iam.gserviceaccount.com
   rm ~/tbmq-kafka-client-key.json
   ```

9. **Delete the network resources you created for this guide.** Skip any that existed before or that other services
   in the project still use: the service connection policy, the HTTPS load balancer's static IP address, and the
   private services access peering and its IP range.

   ```bash
   gcloud network-connectivity service-connection-policies delete tbmq-valkey-policy --region=$GCP_REGION
   gcloud compute addresses delete tbmq-http-lb-address --global
   gcloud services vpc-peerings delete --service=servicenetworking.googleapis.com --network=$GCP_NETWORK
   gcloud compute addresses delete google-managed-services-$GCP_NETWORK --global
   ```

</Steps>
