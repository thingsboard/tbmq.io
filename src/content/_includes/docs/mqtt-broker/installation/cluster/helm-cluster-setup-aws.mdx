This guide covers deploying a TBMQ cluster on Amazon Elastic Kubernetes Service (EKS) with the official Helm
<a href="https://artifacthub.io/packages/helm/tbmq-helm-chart/tbmq-cluster" target="_blank" rel="noopener noreferrer">chart</a>.

The chart deploys only TBMQ: two broker nodes and two Integration Executors. PostgreSQL, Kafka, and a Redis-compatible
cache run separately. This guide deploys them in the cluster with CrunchyData PGO, Strimzi, and Valkey; you can use
Amazon RDS, Amazon MSK, and Amazon ElastiCache instead. Web traffic goes through an AWS Application Load Balancer (ALB)
and MQTT traffic through an AWS Network Load Balancer (NLB).

<Aside>
  This guide names the EKS cluster **`tbmq`**, as the provided `cluster.yml` does. If you change the name, change it in
  every command that uses it: `helm install aws-load-balancer-controller --set clusterName=...` and
  `eksctl delete cluster -n ...`.
</Aside>

### Configure the cluster

Download the EKS cluster configuration:

<Code code={clusterYmlCmd} lang="bash" />

Review these fields in `cluster.yml`:

- `region` and `availabilityZones`: the AWS region and three of its availability zones. The defaults are `us-east-1`
  and `us-east-1a`, `us-east-1b`, `us-east-1c`.
- `version`: the Kubernetes version. List the versions EKS offers in your region with
  `aws eks describe-cluster-versions --region {region} --query 'clusterVersions[].clusterVersion'`.
- `instanceType`: the EC2 instance type of each node group. Not every type is offered in every region; see
  [Check instance types in your region](#check-instance-types-in-your-region).
- `desiredCapacity`: the number of nodes in each node group.
- `volumeType`: the EBS volume type of the node disks, `gp3` by default.

To size the instances for production, see
<a href="https://aws.amazon.com/ec2/instance-types/" target="_blank" rel="noopener noreferrer">Amazon EC2 instance types</a>.

#### Check instance types in your region

The default `c7a` instance types aren't available in every region. Check that the region offers the types in your
`cluster.yml`:

```bash
aws ec2 describe-instance-type-offerings --region us-east-1 --location-type availability-zone \
  --filters Name=instance-type,Values=c7a.large,c7a.medium \
  --query 'InstanceTypeOfferings[].[InstanceType,Location]' --output text
```

Each type must be listed for every zone in `availabilityZones`. If it isn't, pick another type, such as `c7i.large`.

#### Node groups

`cluster.yml` creates a node group for each workload. Each node carries a `role` label, which pins the workload to it:

| Node group        | `role` label | Runs                                    |
|-------------------|--------------|-----------------------------------------|
| `tbmq-node`       | `tbmq`       | TBMQ broker                             |
| `tbmq-ie`         | `tbmq-ie`    | TBMQ Integration Executor               |
| `tbmq-kafka`      | `kafka`      | Kafka, deployed in this guide           |
| `tbmq-redis`      | `redis`      | Valkey, deployed in this guide          |
| `tbmq-postgresql` | `postgresql` | PostgreSQL, deployed in this guide      |

If you use a managed AWS service instead, delete its node group from `cluster.yml` before you create the cluster:
`tbmq-kafka` for Amazon MSK, `tbmq-redis` for Amazon ElastiCache, `tbmq-postgresql` for Amazon RDS.

#### IAM and add-ons

The `iam` block enables
<a href="https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html" target="_blank" rel="noopener noreferrer">IAM roles for service accounts</a>
and creates the `aws-load-balancer-controller` service account with the IAM policy the
<a href="https://docs.aws.amazon.com/eks/latest/userguide/aws-load-balancer-controller.html" target="_blank" rel="noopener noreferrer">AWS Load Balancer Controller</a>
needs:

```yaml
iam:
  withOIDC: true
  serviceAccounts:
    - metadata:
        name: aws-load-balancer-controller
        namespace: kube-system
      wellKnownPolicies:
        awsLoadBalancerController: true
```

The `addons` block installs these EKS add-ons:

- `aws-ebs-csi-driver`: provisions EBS volumes for persistent volume claims. TBMQ and its dependencies need it.
- `aws-efs-csi-driver`: mounts Amazon EFS volumes. TBMQ doesn't use it.
- `vpc-cni`: gives each pod an IP address in the VPC.
- `coredns`: cluster DNS.
- `kube-proxy`: routes Service traffic on each node.

## Deploy PostgreSQL, Kafka, and Valkey

The chart doesn't include PostgreSQL, Kafka, or a Redis-compatible cache. Any instances that TBMQ can reach work. This
section deploys a small set on the dedicated node groups; size it for your load before production. To use managed AWS
services instead, skip to [Use AWS managed services](#use-aws-managed-services).

### PostgreSQL

Install the CrunchyData PGO operator and wait for it:

```bash
helm install pgo oci://registry.developers.crunchydata.com/crunchydata/pgo \
  --version 6.0.1 -n tbmq
kubectl wait --for=condition=Ready pod -l postgres-operator.crunchydata.com/control-plane=pgo \
  -n tbmq --timeout=180s
```

Create a PostgreSQL 17 cluster with the `thingsboard_mqtt_broker` database on the `postgresql` nodes:

```bash
cat <<'EOF' | kubectl apply -n tbmq -f -
apiVersion: postgres-operator.crunchydata.com/v1beta1
kind: PostgresCluster
metadata:
  name: tbmq-db
spec:
  postgresVersion: 17
  instances:
    - name: instance1
      replicas: 1
      dataVolumeClaimSpec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: role
                    operator: In
                    values: ["postgresql"]
  users:
    - name: postgres
      databases:
        - thingsboard_mqtt_broker
  backups:
    pgbackrest:
      repos:
        - name: repo1
          volume:
            volumeClaimSpec:
              accessModes: ["ReadWriteOnce"]
              resources:
                requests:
                  storage: 10Gi
EOF
```

Wait for the database pod. PGO creates it a few seconds after the manifest is applied, so the first command waits for
the pod to exist:

```bash
until kubectl get pod -n tbmq -l postgres-operator.crunchydata.com/data=postgres 2>/dev/null | grep -q tbmq-db; do sleep 3; done
kubectl wait --for=condition=Ready pod -l postgres-operator.crunchydata.com/data=postgres \
  -n tbmq --timeout=300s
```

PGO serves the database at `tbmq-db-primary:5432` and stores the generated password in the Secret
`tbmq-db-pguser-postgres`, key `password`.

### Kafka

Install the Strimzi operator and wait for it:

```bash
helm repo add strimzi https://strimzi.io/charts/
helm repo update
helm install strimzi strimzi/strimzi-kafka-operator --version 0.50.0 -n tbmq
kubectl wait --for=condition=Ready pod -l name=strimzi-cluster-operator -n tbmq --timeout=180s
```

Create a three-node Kafka 4.0 cluster in KRaft mode on the `kafka` nodes:

```bash
cat <<'EOF' | kubectl apply -n tbmq -f -
apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: combined
  labels:
    strimzi.io/cluster: tbmq-kafka
spec:
  replicas: 3
  roles:
    - controller
    - broker
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim
        size: 10Gi
        deleteClaim: false
  resources:
    requests:
      memory: "2Gi"
      cpu: "500m"
    limits:
      memory: "2Gi"
      cpu: "1"
  template:
    pod:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: role
                    operator: In
                    values: ["kafka"]
---
apiVersion: kafka.strimzi.io/v1
kind: Kafka
metadata:
  name: tbmq-kafka
  annotations:
    strimzi.io/node-pools: enabled
    strimzi.io/kraft: enabled
spec:
  kafka:
    version: 4.0.0
    metadataVersion: "4.0"
    listeners:
      - name: plain
        port: 9092
        type: internal
        tls: false
    config:
      auto.create.topics.enable: false
      default.replication.factor: 2
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
  entityOperator:
    topicOperator: {}
    userOperator: {}
EOF
```

Wait for the cluster; this takes a few minutes:

```bash
kubectl wait kafka/tbmq-kafka --for=condition=Ready -n tbmq --timeout=600s
```

Kafka is reachable at `tbmq-kafka-kafka-bootstrap:9092`.

### Use AWS managed services

To use Amazon RDS, Amazon MSK, or Amazon ElastiCache instead of the in-cluster deployments, create them in the VPC that
`eksctl` created for the cluster, and allow traffic from the cluster nodes. The
<DocLink product={props.product} path="installation/cluster/aws-cluster-setup/#create-the-aws-managed-services" bold={false}>AWS cluster setup guide</DocLink>
walks through creating each one. Then set their endpoints in [Connect to dependencies](#connect-to-dependencies)
instead of the in-cluster values:

```yaml
postgresql:
  host: "my-tbmq-db.xxxxxx.us-east-1.rds.amazonaws.com"
  port: 5432
  database: "thingsboard_mqtt_broker"
  username: "postgres"
  existingSecret: "my-pg-secret"
  existingSecretPasswordKey: "password"

kafka:
  bootstrapServers: "b-1.my-msk.xxxxxx.c2.kafka.us-east-1.amazonaws.com:9092,b-2.my-msk.xxxxxx.c2.kafka.us-east-1.amazonaws.com:9092"

redis:
  connectionType: "cluster"
  nodes: "clustercfg.my-cache.xxxxxx.use1.cache.amazonaws.com:6379"
  usePassword: false
```

Create the PostgreSQL password Secret in the `tbmq` namespace first:

```bash
kubectl create secret generic my-pg-secret -n tbmq --from-literal=password='YOUR_DB_PASSWORD'
```

- **Amazon MSK**: get the bootstrap servers with `aws kafka get-bootstrap-brokers --cluster-arn {cluster-arn}`. Port
  `9092` is the plaintext listener. For the TLS listener, use the port `9094` brokers and set
  `TB_KAFKA_DEFAULT_PRODUCER_CONSUMER_CONFIG: "security.protocol:SSL"` in both `tbmq.customEnv` and `tbmq-ie.customEnv`.
  IAM access control isn't supported: the TBMQ images don't include the MSK IAM authentication library.
- **Amazon ElastiCache**: with cluster mode enabled, set `connectionType: "cluster"` and `nodes` to the configuration
  endpoint with port `6379`. With cluster mode disabled, set `connectionType: "standalone"` and `host` to the primary
  endpoint. If the cache uses in-transit encryption, enable TLS in `tbmq.customEnv`. ElastiCache certificates are
  issued by Amazon's root CAs, which the CA bundle in the TBMQ image already contains:

  ```yaml
  tbmq:
    customEnv:
      REDIS_SSL_ENABLED: "true"
      REDIS_SSL_CERT_FILE: "/etc/ssl/certs/ca-certificates.crt"
  ```

For all `postgresql`, `kafka`, and `redis` keys, see the
<a href="https://artifacthub.io/packages/helm/tbmq-helm-chart/tbmq-cluster#step-2-prepare-your-values-yaml" target="_blank" rel="noopener noreferrer">connection settings</a>
in the chart documentation.

### Load balancer configuration

Set the load balancer type to `aws`:

```yaml
loadbalancer:
  type: "aws"
```

The chart then creates two internet-facing load balancers through the AWS Load Balancer Controller:

| Load balancer | Kubernetes resource                 | Ports                                              |
|---------------|-------------------------------------|----------------------------------------------------|
| ALB           | Ingress `my-tbmq-cluster-http-lb`   | `80` (HTTP); `443` (HTTPS) with HTTPS enabled      |
| NLB           | Service `my-tbmq-cluster-mqtt-lb`   | `1883` (MQTT), `8084` (MQTT over WebSockets), `8883` (MQTTS), `8085` (MQTT over secure WebSockets) |

MQTTS and secure WebSockets work only after you configure TLS for them: either
[TLS termination](#tls-termination-one-way-tls) at the NLB or [mutual TLS](#mutual-tls-mtls) in TBMQ.

#### HTTPS access

The ALB serves HTTPS with a certificate from
<a href="https://aws.amazon.com/certificate-manager/" target="_blank" rel="noopener noreferrer">AWS Certificate Manager</a> (ACM).
Request or import a certificate for your domain in the cluster's region and note its ARN. Then enable HTTPS in
`values.yaml`:

```yaml
loadbalancer:
  type: "aws"
  http:
    enabled: true
    ssl:
      enabled: true
      certificateRef: "<your-acm-certificate-arn>"
```

The ALB then listens on `443` and redirects HTTP on `80` to HTTPS. After installing, point your domain at the ALB
address with a DNS `CNAME` record.

#### MQTTS access

##### TLS termination (one-way TLS)

The NLB decrypts MQTTS and secure WebSockets traffic with an ACM certificate and forwards it to TBMQ's plain ports:
`8883` to `1883` and `8085` to `8084`. Traffic between the NLB and TBMQ stays inside your VPC, unencrypted. Set the ACM
certificate ARN in `values.yaml`:

```yaml
loadbalancer:
  type: "aws"
  mqtt:
    enabled: true
    tlsTermination:
      enabled: true
      certificateRef: "<your-acm-certificate-arn>"
```

<Aside type="caution">
  The NLB doesn't pass client certificates to TBMQ, so MQTT clients can't authenticate with X.509 certificates. Use
  [mutual TLS](#mutual-tls-mtls) for that.
</Aside>

<Aside type="tip" title="Allow TLS 1.3">
  The controller gives the ALB and NLB TLS listeners the `ELBSecurityPolicy-2016-08` security policy, which doesn't
  support TLS 1.3. Some clients fail to connect without it; for example, `mosquitto` 2.0 reports `Protocol error`. To
  allow TLS 1.3 and 1.2, set a newer policy through the chart's annotations:

  ```yaml
  loadbalancer:
    http:
      annotations:
        alb.ingress.kubernetes.io/ssl-policy: "ELBSecurityPolicy-TLS13-1-2-2021-06"
    mqtt:
      annotations:
        service.beta.kubernetes.io/aws-load-balancer-ssl-negotiation-policy: "ELBSecurityPolicy-TLS13-1-2-2021-06"
  ```

  When you change the policy on a running release, the NLB takes a few minutes to apply it to all its nodes.
</Aside>

##### Mutual TLS (mTLS)

With mutual TLS, the NLB forwards ports `8883` and `8085` unchanged, and TBMQ terminates TLS itself. This supports
<DocLink product={props.product} path="security/authentication/x509" bold={false}>X.509 certificate authentication</DocLink>.
`mutualTls` takes precedence over `tlsTermination`.

Create a Secret with the server certificate chain and its private key, in PEM format:

```bash
kubectl create secret generic tbmq-mqtts -n tbmq \
  --from-file=server.pem=server-chain.pem \
  --from-file=mqttserver_key.pem=server.key
```

Enable mutual TLS in `values.yaml`:

```yaml
loadbalancer:
  type: "aws"
  mqtt:
    enabled: true
    mutualTls:
      enabled: true
      existingSecretName: "tbmq-mqtts"
```

This enables MQTTS on `8883`. To also serve MQTT over secure WebSockets on `8085` with the same certificate, add to the
`tbmq` section:

```yaml
tbmq:
  customEnv:
    LISTENER_WSS_ENABLED: "true"
    LISTENER_WSS_PEM_CERT: "/ssl-config/server.pem"
    LISTENER_WSS_PEM_KEY: "/ssl-config/mqttserver_key.pem"
```

For a password-protected key and the other options, see
<a href="https://artifacthub.io/packages/helm/tbmq-helm-chart/tbmq-cluster#mutual-tls-mtls-for-mqtt" target="_blank" rel="noopener noreferrer">mutual TLS</a>
in the chart documentation.

## Install the TBMQ Helm chart

From the directory with your `values.yaml`, install the chart:

```bash
helm install my-tbmq-cluster tbmq-helm-chart/tbmq-cluster -n tbmq \
  -f values.yaml \
  --set installation.installDbSchema=true
```

`my-tbmq-cluster` is the Helm release name. It prefixes every resource the chart creates, and later `helm` commands
refer to it.

Helm runs a one-time install pod that creates the database schema and returns when the pod succeeds, usually within a
minute:

```text
NAME: my-tbmq-cluster
NAMESPACE: tbmq
STATUS: deployed
REVISION: 1
...
```

The broker pods start after the schema exists. Wait until they are ready:

```bash
kubectl rollout status statefulset/my-tbmq-cluster-tbmq-node -n tbmq --timeout=600s
```

The ALB takes a few minutes to provision. Then open `http://{ADDRESS}` in your browser, or your domain over HTTPS if

## Validate MQTT access

Get the address of the NLB:

```bash
kubectl get svc my-tbmq-cluster-mqtt-lb -n tbmq
```

```text
NAME                      TYPE           CLUSTER-IP       EXTERNAL-IP                                                                 PORT(S)                                                       AGE
my-tbmq-cluster-mqtt-lb   LoadBalancer   10.100.193.186   k8s-tbmq-mytbmqcl-58441a19fc-c53931afca4eb86a.elb.us-east-1.amazonaws.com   1883:30292/TCP,8084:31184/TCP,8883:30290/TCP,8085:30962/TCP   3m
```

MQTT clients connect to `EXTERNAL-IP` on port `1883`, and MQTT over WebSockets on port `8084`. The NLB address
resolves a few minutes after it is created.

To check the broker end to end, publish and subscribe with the
<a href="https://mosquitto.org/download/" target="_blank" rel="noopener noreferrer">Mosquitto clients</a>. A new
installation has one MQTT credential, **TBMQ WebSockets MQTT Credentials**: username `tbmq_websockets_username` and no
password. In one terminal, subscribe:

```bash
mosquitto_sub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/#' -v -q 1
```

In another, publish:

```bash
mosquitto_pub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/hello' -m 'hello from eks' -q 1
```

The subscriber prints `tbmq/demo/hello hello from eks`. A client that connects without a username is refused as not
authorized, because MQTT Basic authentication is enabled by default. To create your own credentials, see
<DocLink product={props.product} path="user-guide/ui/mqtt-client-credentials" bold={false}>MQTT client credentials</DocLink>.

## Troubleshooting

List the TBMQ pods:

```bash
kubectl get pods -n tbmq -l 'app in (my-tbmq-cluster-tbmq-node,my-tbmq-cluster-tbmq-ie,install-job)'
```

View the logs of a broker node:

```bash
kubectl logs -f my-tbmq-cluster-tbmq-node-0 -n tbmq
```

If `helm install` fails with `failed post-install`, the schema install did not succeed. Read the install pod's logs:

```bash
kubectl logs my-tbmq-cluster-install-pod -n tbmq
```

Broker pods that stay in `Init:0/1` are waiting for the schema. For the common causes and fixes, see
<a href="https://artifacthub.io/packages/helm/tbmq-helm-chart/tbmq-cluster#troubleshooting-the-install" target="_blank" rel="noopener noreferrer">Troubleshooting the install</a>
in the chart documentation.

If the Ingress `ADDRESS` or the Service `EXTERNAL-IP` stays empty, the AWS Load Balancer Controller couldn't create the
load balancer. Its events and logs give the reason:

```bash
kubectl describe ingress my-tbmq-cluster-http-lb -n tbmq
kubectl describe svc my-tbmq-cluster-mqtt-lb -n tbmq
kubectl logs deployment/aws-load-balancer-controller -n kube-system
```

<ShowFor product={props.product} show={[Products.TBMQ_PE]}>

<ConditionalHeading level={3} id="upgrade-from-ce-to-pe" showFor="mqtt-broker-pe">Upgrade from TBMQ to TBMQ PE</ConditionalHeading>

To move a Community Edition release to PE, first upgrade it to the same TBMQ version as the target PE release. Then:

<Steps>

1. **Switch `values.yaml` to PE.**

   In the `values.yaml` of your CE release, set the PE images and the license exactly as for a fresh PE install: see
   [Configure license and broker images](#configure-license-and-broker-images), including the license Secret.

2. **Stop TBMQ.**

   Scale the broker and Integration Executor to zero so nothing uses the database while it is migrated:

   ```bash
   kubectl scale statefulset/my-tbmq-cluster-tbmq-node --replicas=0 -n tbmq
   kubectl scale statefulset/my-tbmq-cluster-tbmq-ie --replicas=0 -n tbmq
   ```

3. **Run the upgrade.**

   ```bash
   helm upgrade my-tbmq-cluster tbmq-helm-chart/tbmq-cluster -n tbmq \
     -f values.yaml \
     --set upgrade.upgradeDbSchema=true \
     --set upgrade.fromVersion=ce
   ```

   The migration converts the database to PE, then Helm starts the broker and Integration Executor on the PE images
   with their usual replica count.

</Steps>

Pass `upgrade.fromVersion=ce` only for this migration. On later PE upgrades, leave it out: with it, the migration fails.

</ShowFor>

### Run upgrade

<Steps>

1. **Update the chart repository.**

   ```bash
   helm repo update
   ```

2. **Compare versions.**

   The `APP VERSION` column is the TBMQ version. Compare your release with the latest chart:

   ```bash
   helm list -n tbmq
   helm search repo tbmq-helm-chart/tbmq-cluster
   ```

3. **Update `values.yaml`.**

   Export the new defaults and compare them with your file:

   ```bash
   helm show values tbmq-helm-chart/tbmq-cluster > values-new.yaml
   diff values.yaml values-new.yaml
   ```

   Carry the changes you need into `values.yaml`. Always update the image tags, or the release keeps running the old
   TBMQ version:

   <Code code={props.product === Products.TBMQ_PE ? peTagsYaml : ceTagsYaml} lang="yaml" />

4. **Run the upgrade.**

   ```bash
   helm upgrade my-tbmq-cluster tbmq-helm-chart/tbmq-cluster -n tbmq \
     -f values.yaml \
     --set upgrade.upgradeDbSchema=true
   ```

   A pre-upgrade job migrates the database, then Kubernetes replaces the TBMQ pods one at a time, each after the
   previous one is ready. Wait for it to finish:

   ```bash
   kubectl rollout status statefulset/my-tbmq-cluster-tbmq-node -n tbmq --timeout=600s
   ```

</Steps>

If the `APP VERSION` doesn't change, there is nothing to migrate: run the same `helm upgrade` without
`--set upgrade.upgradeDbSchema=true`. With it, the migration fails with `database already upgraded to current version`
and the release is marked `failed`; running the upgrade again without the flag fixes it.

<Aside title="Upgrades that stop TBMQ">
  Upgrades to 2.4.0 and later are rolling upgrades: Kubernetes replaces the TBMQ pods one at a time, so the cluster keeps
  accepting connections. Upgrades to 2.3.0 and earlier must stop every TBMQ node while the database is migrated — see
  the <DocLink product={props.product} path="installation/upgrade-instructions/#downtime" bold={false}>downtime of each version</DocLink>.
  For those, scale the TBMQ pods to zero before `helm upgrade`; Helm starts them again:

  ```bash
  kubectl scale statefulset/my-tbmq-cluster-tbmq-node --replicas=0 -n tbmq
  kubectl scale statefulset/my-tbmq-cluster-tbmq-ie --replicas=0 -n tbmq
  ```
</Aside>

<Aside type="tip">
  To upgrade to a specific version, add `--version {chart-version}` to `helm show values` and `helm upgrade`.
  `helm search repo tbmq-helm-chart/tbmq-cluster --versions` lists each chart version with its TBMQ version.
  TBMQ versions must be upgraded one at a time: if you are more than one version behind, run the upgrade once for each
  TBMQ version in between, with the chart version for it.
</Aside>

Chart 2.0.0 (TBMQ 2.3.0) removed the PostgreSQL, Kafka, and Redis subcharts that chart 1.x bundled. To upgrade a
release from chart 1.x, follow
<a href="https://github.com/thingsboard/helm-charts/tree/main/tbmq#upgrading-from-chart-version-1x-to-200-tbmq-220--230" target="_blank" rel="noopener noreferrer">Upgrading from chart version 1.x to 2.0.0</a>
in the chart documentation.

## Uninstalling TBMQ Helm chart

```bash
helm uninstall my-tbmq-cluster -n tbmq
```

This removes the TBMQ resources of the release, and the AWS Load Balancer Controller deletes the ALB and the NLB. It
keeps the broker's data volumes; delete them with:

```bash
kubectl delete pvc -n tbmq -l app=my-tbmq-cluster-tbmq-node
```

PostgreSQL, Kafka, and Valkey keep running.

<ShowFor product={props.product} show={[Products.TBMQ_PE]}>
The `tbmq-license` Secret is kept as well.
</ShowFor>

To remove them too, delete the database and Kafka clusters while their operators still run, then the operators, Valkey,
and the namespace:

```bash
kubectl delete postgrescluster tbmq-db -n tbmq
kubectl delete kafka tbmq-kafka -n tbmq
kubectl delete kafkanodepool combined -n tbmq
helm uninstall valkey strimzi pgo -n tbmq
kubectl delete namespace tbmq
```

Deleting the namespace first leaves it stuck in `Terminating`: the operators are removed before they can clean up their
clusters. Deleting the namespace also deletes the remaining volumes and their EBS disks.

Amazon RDS, MSK, and ElastiCache instances aren't affected; delete them in the AWS console if you no longer need them.

## Delete the EKS cluster

Uninstall TBMQ first, as in the previous section. A load balancer that still exists when the cluster is deleted is left
behind and keeps the VPC from being deleted.

```bash
helm uninstall aws-load-balancer-controller -n kube-system
eksctl delete cluster -r us-east-1 -n tbmq -w
```

Use your cluster's region in `-r`. The deletion takes about 15 minutes.
