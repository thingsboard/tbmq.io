This guide covers deploying a TBMQ cluster on Amazon Elastic Kubernetes Service (EKS) with the TBMQ Kubernetes scripts.

The scripts deploy two TBMQ broker nodes and two Integration Executors. TBMQ stores its data in Amazon RDS for
PostgreSQL, Amazon MSK (Kafka), and Amazon ElastiCache (Valkey), which you create in the AWS Console. Web traffic goes
through an AWS Application Load Balancer (ALB) and MQTT traffic through an AWS Network Load Balancer (NLB).

## Configure your Kubernetes environment

### Configure AWS tools

Set your access key, secret key, and default region:

```bash
aws configure
```

To create access keys, see
<a href="https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html" target="_blank" rel="noopener noreferrer">Manage access keys for IAM users</a>.

### Configure the cluster

Review these fields in `cluster.yml`:

- `region` and `availabilityZones`: the AWS region and three of its availability zones. The defaults are `us-east-1`
  and `us-east-1a`, `us-east-1b`, `us-east-1c`.
- `version`: the Kubernetes version. List the versions EKS offers in your region with
  `aws eks describe-cluster-versions --region {region} --query 'clusterVersions[].clusterVersion'`.
- `instanceType`: the EC2 instance type of each node group, `m7a.large` by default. Not every type is offered in every
  region; see [Check instance types in your region](#check-instance-types-in-your-region).
- `desiredCapacity`: the number of nodes in each node group, `2` by default.

To size the instances for production, see
<a href="https://aws.amazon.com/ec2/instance-types/" target="_blank" rel="noopener noreferrer">Amazon EC2 instance types</a>.

#### Check instance types in your region

Check that the region offers the instance type in your `cluster.yml`:

```bash
aws ec2 describe-instance-type-offerings --region us-east-1 --location-type availability-zone \
  --filters Name=instance-type,Values=m7a.large \
  --query 'InstanceTypeOfferings[].[InstanceType,Location]' --output text
```

The type must be listed for every zone in `availabilityZones`. If it isn't, pick another type, such as `m7i.large`.

#### Node groups

`cluster.yml` creates two node groups in private subnets. Each node carries a `role` label, which pins the workload
to it:

| Node group | `role` label | Runs                      |
|------------|--------------|---------------------------|
| `managed`  | `tbmq`       | TBMQ broker               |
| `tbmq-ie`  | `tbmq-ie`    | TBMQ Integration Executor |

The broker and the Integration Executor each run two replicas on separate nodes, so each group needs at least two
nodes. To run both on the same nodes, give the nodes both labels or change `nodeSelector` in `tbmq-ie.yml`.

#### IAM and add-ons

The `iam` block enables
<a href="https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html" target="_blank" rel="noopener noreferrer">IAM roles for service accounts</a>
and creates the `aws-load-balancer-controller` service account with the IAM policy the
<a href="https://docs.aws.amazon.com/eks/latest/userguide/aws-load-balancer-controller.html" target="_blank" rel="noopener noreferrer">AWS Load Balancer Controller</a>
needs:

```yaml
iam:
  withOIDC: true
  serviceAccounts:
    - metadata:
        name: aws-load-balancer-controller
        namespace: kube-system
      wellKnownPolicies:
        awsLoadBalancerController: true
```

The `addons` block installs these EKS add-ons:

- `aws-ebs-csi-driver`: provisions EBS volumes for persistent volume claims.
- `vpc-cni`: gives each pod an IP address in the VPC.
- `coredns`: cluster DNS.
- `kube-proxy`: routes Service traffic on each node.

### Create the EKS cluster

```bash
eksctl create cluster -f cluster.yml
```

This takes about 20 minutes. When it finishes, `eksctl` adds the cluster to your kubeconfig and switches the current
context to it.

<Aside type="caution" title="Check the kubectl context">
  Every command in this guide runs against your current kubectl context. If you switched it since `eksctl create cluster`,
  switch back first. This command must print a name that ends with `@tbmq.{region}.eksctl.io`:

  ```bash
  kubectl config current-context
  ```
</Aside>

```bash
kubectl apply -f gp3-def-sc.yml
kubectl get sc
```

```text
gp2             kubernetes.io/aws-ebs   Delete          WaitForFirstConsumer   false                  15m
gp3 (default)   ebs.csi.aws.com         Delete          WaitForFirstConsumer   true                   5s
```

`gp3` must be the only default. If `gp2` is also marked `(default)`, remove its flag:

```bash
kubectl patch storageclass gp2 -p '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"false"}}}'
```

### Install the AWS Load Balancer Controller

The controller creates the ALB and the NLB for TBMQ. `eksctl` already created its service account and IAM role, so
install it with that service account:

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo update
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=tbmq \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller
kubectl rollout status deployment/aws-load-balancer-controller -n kube-system --timeout=180s
```

## Create the AWS managed services

Create the PostgreSQL database, the Kafka cluster, and the Valkey cache in the VPC that `eksctl` created for the
cluster, in its private subnets, and attach the `eksctl-tbmq-cluster-ClusterSharedNodeSecurityGroup-*` security
group to each. That security group allows traffic from the cluster nodes, so TBMQ can reach the services without
further rules. To find the VPC, the private subnets, and the security group:

```bash
aws cloudformation describe-stacks --region us-east-1 --stack-name eksctl-tbmq-cluster \
  --query "Stacks[0].Outputs[?OutputKey=='VPC' || OutputKey=='SubnetsPrivate' || OutputKey=='SharedNodeSecurityGroup'].[OutputKey,OutputValue]" \
  --output text
```

In the AWS Console, the VPC is named `eksctl-tbmq-cluster/VPC`. Create the three services in the cluster's region. You
can create them in parallel; Amazon MSK takes the longest, about 30 minutes.

### Amazon RDS (PostgreSQL)

Create a PostgreSQL database on Amazon RDS. To get started, follow the
<a href="https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_SettingUp.html" target="_blank" rel="noopener noreferrer">official AWS RDS setup guide</a>.

Recommendations:

- **PostgreSQL version**: Use **17.x**.
- **Template**: Use **Production** for real workloads. It enables important resilience settings by default.
- **Availability**: Enable **Multi-AZ deployment** for automatic failover.
- **Credentials**: Change the default `username` and set a secure `password`. You need both to configure TBMQ.
- **Instance**: Use a general-purpose Graviton instance like `db.m7g.large`. Right-size first, optimize later.
- **Scaling**: Scale vertically (instance class/size) if sustained CPU exceeds 80% or active connections near limits. Change type during a maintenance window.
- **Storage**: Choose **gp3 or io1** for production.
- **Connectivity**: Choose the cluster's VPC, keep **Public access** set to **No**, and attach the
  `eksctl-tbmq-cluster-ClusterSharedNodeSecurityGroup-*` security group.
- **Parameter group**: Create a custom parameter group for easier future adjustments.
- **Initial database name**: Set to `thingsboard_mqtt_broker` under **Additional configuration**. TBMQ connects to this
  database; RDS doesn't create it unless you set the name.
- **Monitoring**: Enable enhanced monitoring and CloudWatch alarms for key metrics.

### Amazon MSK (Kafka)

Create an Amazon MSK cluster. Open the AWS Console → **MSK** → **Create cluster** → **Custom create**.

Recommendations:

- **Cluster type**: Select **Provisioned** for full control over capacity and configuration.
- **Kafka version**: Use **4.0.x** in **KRaft** metadata mode, the Kafka version TBMQ's other deployments run.
- **Instance type**: Start with `kafka.m7g.large` brokers. Scale up later if needed.
- **Cluster configuration**: Create a custom configuration for easier future parameter changes.
- **Networking**: Choose the cluster's VPC and its **private subnets**, one per availability zone. Attach the

### Amazon ElastiCache (Valkey)

TBMQ uses Valkey to store messages for
<DocLink product={props.product} path="architecture/#persistent-device-client">DEVICE persistent clients</DocLink>
and to cache MQTT client credentials. Without the cache, every new connection queries the database to validate its
credentials, which can overload the database under high connection rates.

Open the AWS Console → **ElastiCache** → **Valkey caches** → **Create cache**.

Recommendations:

- **Deployment**: Choose **Design your own cache** → **Cluster cache**.
- **Cluster mode**: **Enabled** for production, which this guide uses. **Disabled** runs a single primary node with
  optional replicas; TBMQ supports both.
- **Engine version**: Use **8.x**.
- **Node type**: Start with `cache.r7g.large`; at least **1 GB RAM** for dev/test.
- **Shards**: For production, configure **3 shards** with **1 replica per shard**.
- **Parameter groups**: Use the default Valkey 8.x group or create a custom parameter group for easier tuning later.
- **Networking**: Choose the cluster's VPC and its **private subnets**. Attach the
  `eksctl-tbmq-cluster-ClusterSharedNodeSecurityGroup-*` security group.
- **Encryption in transit**: Check this setting before you create the cache. TBMQ connects without TLS by default, so
  if encryption in transit is enabled, [enable TLS in TBMQ](#connect-to-amazon-elasticache). Encryption at rest
  doesn't affect TBMQ.
- **Access control**: Leave it off, or set a password and pass it to TBMQ as `REDIS_PASSWORD`.
- **Backups**: Enable automatic backups with a 1–7 day retention period.

## Connect TBMQ to the managed services

### Connect to Amazon RDS

Once the database is **Available**, get its endpoint. `{db-identifier}` is the DB identifier you set when you created
it:

```bash
aws rds describe-db-instances --region us-east-1 --db-instance-identifier {db-identifier} \
  --query 'DBInstances[0].Endpoint.Address' --output text
```

<ImageGallery images={[
  { src: '/src/assets/images/docs/mqtt-broker/install/aws-rds-endpoint.png', alt: 'AWS RDS Details', caption: 'AWS RDS Details' },
]} />

In `tbmq-db-configmap.yml`, replace `RDS_URL_HERE` in `SPRING_DATASOURCE_URL` with the endpoint, and set the
username and password you chose:

```yaml
  SPRING_DATASOURCE_URL: "jdbc:postgresql://my-tbmq-db.xxxxxx.us-east-1.rds.amazonaws.com:5432/thingsboard_mqtt_broker"
  SPRING_DATASOURCE_USERNAME: "YOUR_RDS_POSTGRES_USER"
  SPRING_DATASOURCE_PASSWORD: "YOUR_RDS_POSTGRES_PASSWORD"
```

### Connect to Amazon MSK

Once the MSK cluster is **Active**, get its bootstrap servers. `{cluster-arn}` is the cluster's ARN, shown on its
details page:

```bash
aws kafka get-bootstrap-brokers --region us-east-1 --cluster-arn {cluster-arn}
```

<ImageGallery images={[
  { src: '/src/assets/images/docs/mqtt-broker/install/aws-msk-arn.png', alt: 'AWS MSK Details', caption: 'AWS MSK Details' },
]} />

Copy the `BootstrapBrokerString` value, the plaintext brokers on port `9092`. In both `tbmq.yml` and `tbmq-ie.yml`,
replace `PUT_YOUR_KAFKA_SERVERS_HERE` with it:

```yaml
            - name: TB_KAFKA_SERVERS
              value: "b-1.my-msk.xxxxxx.c2.kafka.us-east-1.amazonaws.com:9092,b-2.my-msk.xxxxxx.c2.kafka.us-east-1.amazonaws.com:9092"
```

To connect over TLS instead, copy `BootstrapBrokerStringTls`, the brokers on port `9094`, and add this variable next to
`TB_KAFKA_SERVERS` in both files:

```yaml
            - name: TB_KAFKA_DEFAULT_PRODUCER_CONSUMER_CONFIG
              value: "security.protocol:SSL"
```

### Connect to Amazon ElastiCache

Once the cache is **Available**, get its endpoint. `{cache-name}` is the name you gave the cache:

```bash
aws elasticache describe-replication-groups --region us-east-1 --replication-group-id {cache-name} \
  --query 'ReplicationGroups[0].[ConfigurationEndpoint.Address,NodeGroups[0].PrimaryEndpoint.Address]' --output text
```

With cluster mode enabled, the command prints the configuration endpoint; with cluster mode disabled, it prints `None`
and the primary endpoint.

<ImageGallery images={[
  { src: '/src/assets/images/docs/mqtt-broker/install/aws-redis-result.png', alt: 'AWS ElastiCache Details', caption: 'AWS ElastiCache Details' },
]} />

Set the endpoint in `tbmq-cache-configmap.yml`. With cluster mode enabled, set the configuration endpoint with port
`6379` in `REDIS_NODES`:

```yaml
  REDIS_CONNECTION_TYPE: "cluster"
  REDIS_NODES: "clustercfg.my-cache.xxxxxx.use1.cache.amazonaws.com:6379"
```

With cluster mode disabled, set the primary endpoint, without the port, in `REDIS_HOST`:

```yaml
  REDIS_CONNECTION_TYPE: "standalone"
  REDIS_HOST: "master.my-cache.xxxxxx.use1.cache.amazonaws.com"
```

If you enabled encryption in transit, also add:

```yaml
  REDIS_SSL_ENABLED: "true"
  REDIS_SSL_CERT_FILE: "/etc/ssl/certs/ca-certificates.crt"
```

ElastiCache certificates are issued by Amazon's root CAs, which the CA bundle in the TBMQ image already contains. If
you set a password, uncomment `REDIS_PASSWORD` and set it.

## Configure load balancers

The `receipts` directory holds one manifest per load balancer. The AWS Load Balancer Controller creates an
internet-facing load balancer for each one you apply:

| Manifest                        | Load balancer | Ports                                                                                     |
|---------------------------------|---------------|-------------------------------------------------------------------------------------------|
| `http-load-balancer.yml`        | ALB           | `80` (HTTP)                                                                               |
| `https-load-balancer.yml`       | ALB           | `443` (HTTPS); `80` redirects to HTTPS                                                    |
| `mqtt-load-balancer.yml`        | NLB           | `1883` (MQTT), `8084` (MQTT over WebSockets); `8883` and `8085` passed through to TBMQ    |
| `mqtts-load-balancer.yml`       | NLB           | `1883`, `8084`; `8883` (MQTTS) and `8085` (MQTT over secure WebSockets) with TLS termination |

Apply one ALB manifest and one NLB manifest. The HTTPS and one-way TLS manifests set the
`ELBSecurityPolicy-TLS13-1-2-2021-06` security policy, which allows TLS 1.3 and 1.2.

### HTTP load balancer

<Aside>Suitable for development only. For production, use the [HTTPS load balancer](#https-load-balancer) instead.</Aside>

```bash
kubectl apply -f receipts/http-load-balancer.yml
```

### HTTPS load balancer

The ALB serves HTTPS with a certificate from
<a href="https://aws.amazon.com/certificate-manager/" target="_blank" rel="noopener noreferrer">AWS Certificate Manager</a> (ACM).
Request or import a certificate for your domain in the cluster's region and note its ARN. In
`receipts/https-load-balancer.yml`, replace `YOUR_HTTPS_CERTIFICATE_ARN` with it, then apply the manifest:

```bash
kubectl apply -f receipts/https-load-balancer.yml
```

After the ALB is created, point your domain at its address with a DNS `CNAME` record.

### MQTT load balancer

```bash
kubectl apply -f receipts/mqtt-load-balancer.yml
```

This NLB serves plain MQTT. It also forwards ports `8883` and `8085` to TBMQ unchanged, which serves them only with
[two-way TLS](#mqtt-load-balancer-with-two-way-tls).

### MQTT load balancer with one-way TLS

The NLB decrypts MQTTS and secure WebSockets traffic with an ACM certificate and forwards it to TBMQ's plain ports:
`8883` to `1883` and `8085` to `8084`. Traffic between the NLB and TBMQ stays inside your VPC, unencrypted.

<Aside type="caution">
  The NLB doesn't pass client certificates to TBMQ, so MQTT clients can't authenticate with X.509 certificates. Use
  [two-way TLS](#mqtt-load-balancer-with-two-way-tls) for that.
</Aside>

Request or import a certificate in ACM and note its ARN. In `receipts/mqtts-load-balancer.yml`, replace
`YOUR_MQTTS_CERTIFICATE_ARN` with it, then apply the manifest instead of `mqtt-load-balancer.yml`:

```bash
kubectl apply -f receipts/mqtts-load-balancer.yml
```

### MQTT load balancer with two-way TLS

With two-way TLS, the NLB forwards ports `8883` and `8085` unchanged, and TBMQ terminates TLS itself. This supports
<DocLink product={props.product} path="security/authentication/x509" bold={false}>X.509 certificate authentication</DocLink>.

Prepare the server certificate chain and its private key in PEM format; see
<DocLink product={props.product} path="security/mqtts" bold={false}>MQTT over SSL</DocLink>. Create a ConfigMap from
them. The same command replaces the files when you renew the certificate:

```bash
kubectl create configmap tbmq-mqtts-config -n thingsboard-mqtt-broker \
  --from-file=server.pem=YOUR_PEM_FILENAME \
  --from-file=mqttserver_key.pem=YOUR_PEM_KEY_FILENAME \
  -o yaml --dry-run=client | kubectl apply -f -
```

Where:

- `YOUR_PEM_FILENAME`: the server certificate chain file.
- `YOUR_PEM_KEY_FILENAME`: the server certificate's private key file.

In `tbmq.yml`, uncomment the three blocks marked `Uncomment the following lines to enable two-way MQTTS`. They mount
the certificate and enable MQTTS on `8883` and MQTT over secure WebSockets on `8085`.

Apply the updated `tbmq.yml`, which restarts the broker nodes one at a time, and the transparent NLB:

```bash
kubectl apply -f tbmq.yml
kubectl apply -f receipts/mqtt-load-balancer.yml
```

Get the address of the NLB:

```bash
kubectl get svc -n thingsboard-mqtt-broker
```

```text
NAME                        TYPE           CLUSTER-IP       EXTERNAL-IP                                                                     PORT(S)                                                       AGE
tbmq                        ClusterIP      10.100.42.17     <none>                                                                          8083/TCP,1883/TCP,8883/TCP,8084/TCP,8085/TCP                  10m
tbmq-integration-executor   ClusterIP      10.100.12.121    <none>                                                                          8082/TCP                                                      10m
tbmq-mqtt-loadbalancer      LoadBalancer   10.100.119.170   k8s-thingsbo-tbmqmqtt-b9f99d1ab6-1049a98ba4e28403.elb.us-east-1.amazonaws.com   1883:30308/TCP,8084:31760/TCP,8883:31609/TCP,8085:30172/TCP   3m
```

MQTT clients connect to the `EXTERNAL-IP` of `tbmq-mqtt-loadbalancer`, or `tbmq-mqtts-loadbalancer` for one-way TLS, on
the ports listed in [Configure load balancers](#configure-load-balancers). The NLB address resolves a few minutes after
it is created.

To check the broker end to end, publish and subscribe with the
<a href="https://mosquitto.org/download/" target="_blank" rel="noopener noreferrer">Mosquitto clients</a>. A new
installation has one MQTT credential, **TBMQ WebSockets MQTT Credentials**: username `tbmq_websockets_username` and no
password. In one terminal, subscribe:

```bash
mosquitto_sub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/#' -v -q 1
```

In another, publish:

```bash
mosquitto_pub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/hello' -m 'hello from eks' -q 1
```

The subscriber prints `tbmq/demo/hello hello from eks`. A client that connects without a username is refused as not
authorized, because MQTT Basic authentication is enabled by default. To create your own credentials, see
<DocLink product={props.product} path="user-guide/ui/mqtt-client-credentials" bold={false}>MQTT client credentials</DocLink>.

## Troubleshooting

View the logs of a broker node:

```bash
kubectl logs -f tbmq-0 -n thingsboard-mqtt-broker
```

Check the state of the StatefulSets:

```bash
kubectl get statefulsets -n thingsboard-mqtt-broker
```

If a broker node logs connection errors to PostgreSQL, Kafka, or Valkey, check the endpoint you set and that the service
has the `eksctl-tbmq-cluster-ClusterSharedNodeSecurityGroup-*` security group attached.

If the Ingress `ADDRESS` or the Service `EXTERNAL-IP` stays empty, the AWS Load Balancer Controller couldn't create the
load balancer. Its events and logs give the reason:

```bash
kubectl describe ingress -n thingsboard-mqtt-broker
kubectl describe svc tbmq-mqtt-loadbalancer -n thingsboard-mqtt-broker
kubectl logs deployment/aws-load-balancer-controller -n kube-system
```

See the <a href="https://kubernetes.io/docs/reference/kubectl/cheatsheet/" target="_blank" rel="noopener noreferrer">kubectl Cheat Sheet</a> for more details.

```bash

git commit -m "TBMQ configuration"
```

  Both commands are required. `k8s-upgrade-tbmq.sh` upgrades the database but does not touch the TBMQ pods — they keep

</Aside>

## Cluster deletion

<Steps>

1. **Delete the TBMQ nodes.**

   ```bash
   ./k8s-delete-tbmq.sh
   ```

2. **Delete every resource in the `thingsboard-mqtt-broker` namespace**, including the load balancer Ingress and Services:

   ```bash
   ./k8s-delete-all.sh
   ```

3. **Wait for the load balancers to go.** The AWS Load Balancer Controller then deletes the ALB and the NLB. Wait until
   this command lists no load balancer whose name starts with `k8s-thingsbo`:

   ```bash
   aws elbv2 describe-load-balancers --region us-east-1 --query 'LoadBalancers[].LoadBalancerName'
   ```

4. **Delete the managed services.** Delete the Amazon RDS database, the Amazon MSK cluster, and the Amazon ElastiCache
   cache in the AWS Console, and wait until they are deleted. They use the cluster's VPC and security group, so `eksctl`
   can't delete the cluster while they exist. Then delete the subnet groups created for them: the DB subnet group in
   **RDS** → **Subnet groups** and the cache subnet group in **ElastiCache** → **Subnet groups**. Deleting the database
   and the cache doesn't remove them.

5. **Delete the controller and the EKS cluster** (update the cluster name and region if different):

   ```bash
   helm uninstall aws-load-balancer-controller -n kube-system
   eksctl delete cluster -r us-east-1 -n tbmq -w
   ```

</Steps>
