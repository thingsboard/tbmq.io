This guide covers deploying a TBMQ cluster on Google Kubernetes Engine (GKE) with the official Helm
<a href="https://artifacthub.io/packages/helm/tbmq-helm-chart/tbmq-cluster" target="_blank" rel="noopener noreferrer">chart</a>.

The chart deploys only TBMQ: two broker nodes and two Integration Executors. PostgreSQL, Kafka, and a Redis-compatible
cache run separately. This guide deploys them in the cluster with CrunchyData PGO, Strimzi, and Valkey; you can use
Cloud SQL for PostgreSQL, Google Cloud Managed Service for Apache Kafka, and Memorystore for Valkey instead. Web traffic
goes through a Google Cloud Application Load Balancer and MQTT traffic through a passthrough Network Load Balancer.

## Configure your Kubernetes environment

### Configure GCP tools

Create a Google Cloud project (recommended) or choose an existing one, then sign in and select it:

```bash
gcloud init
```

Enable the GKE API:

```bash
gcloud services enable container.googleapis.com
```

### Define environment variables

The commands in this guide read these variables. Set them in the shell you run the guide from; if you open a new
shell, set them again:

```bash
export GCP_PROJECT=$(gcloud config get-value project)
export GCP_REGION=us-central1
export GCP_ZONE1=us-central1-a
export GCP_ZONE2=us-central1-b
export GCP_ZONE3=us-central1-c
export GCP_NETWORK=default
export TB_CLUSTER_NAME=tbmq-cluster
export TB_DATABASE_NAME=tbmq-db
export TB_KAFKA_NAME=tbmq-kafka
export TB_VALKEY_NAME=tbmq-valkey
echo "Project: $GCP_PROJECT, region: $GCP_REGION, network: $GCP_NETWORK"
echo "Zones: $GCP_ZONE1,$GCP_ZONE2,$GCP_ZONE3"
```

Where:

- `GCP_PROJECT`: the project selected in your `gcloud` configuration.
- `GCP_REGION` and `GCP_ZONE1`–`GCP_ZONE3`: a
  <a href="https://docs.cloud.google.com/compute/docs/regions-zones#available" target="_blank" rel="noopener noreferrer">compute region</a>
  and three of its zones.
- `GCP_NETWORK`: the VPC network, `default` for the network every new project has. Its subnet in each region is also
  named `default`; the managed services commands name the subnet with `$GCP_NETWORK` too, so if you use another
  network, give the subnet the same name or edit those commands.
- `TB_CLUSTER_NAME`: the name of the GKE cluster.
- `TB_DATABASE_NAME`, `TB_KAFKA_NAME`, `TB_VALKEY_NAME`: the names of the Cloud SQL instance, the Kafka cluster, and the
  Valkey instance. You need them only if you [use Google Cloud managed services](#use-google-cloud-managed-services).

### Create the GKE cluster

Create a regional cluster with one `e2-standard-4` node in each of the three zones. TBMQ and the dependencies this
guide deploys share these nodes. To size the nodes for production, change `--machine-type` and `--num-nodes`; see
<a href="https://docs.cloud.google.com/compute/docs/machine-resource" target="_blank" rel="noopener noreferrer">machine families</a>.

```bash
gcloud container clusters create $TB_CLUSTER_NAME \
  --release-channel stable \
  --region $GCP_REGION \
  --network=$GCP_NETWORK \
  --node-locations $GCP_ZONE1,$GCP_ZONE2,$GCP_ZONE3 \
  --enable-ip-alias \
  --num-nodes=1 \
  --node-labels=role=main \
  --machine-type=e2-standard-4
```

This takes about 10 minutes. When it finishes, `gcloud` adds the cluster to your kubeconfig and switches the current
context to it. To get the credentials again later, for example on another machine:

```bash
gcloud container clusters get-credentials $TB_CLUSTER_NAME --region $GCP_REGION
```

<Aside type="caution" title="Check the kubectl context">
  Every command in this guide runs against your current kubectl context. If you switched it, switch back first. This
  command must print `gke_{project}_{region}_tbmq-cluster`:

  ```bash
  kubectl config current-context
  ```
</Aside>

## Deploy PostgreSQL, Kafka, and Valkey

The chart doesn't include PostgreSQL, Kafka, or a Redis-compatible cache. Any instances that TBMQ can reach work. This
section deploys a small set in the cluster; size it for your load before production. To use Google Cloud managed
services instead, skip to [Use Google Cloud managed services](#use-google-cloud-managed-services).

### PostgreSQL

Install the CrunchyData PGO operator and wait for it:

```bash
helm install pgo oci://registry.developers.crunchydata.com/crunchydata/pgo \
  --version 6.0.1 -n tbmq
kubectl wait --for=condition=Ready pod -l postgres-operator.crunchydata.com/control-plane=pgo \
  -n tbmq --timeout=180s
```

Create a PostgreSQL 17 cluster with the `thingsboard_mqtt_broker` database:

```bash
cat <<'EOF' | kubectl apply -n tbmq -f -
apiVersion: postgres-operator.crunchydata.com/v1beta1
kind: PostgresCluster
metadata:
  name: tbmq-db
spec:
  postgresVersion: 17
  instances:
    - name: instance1
      replicas: 1
      dataVolumeClaimSpec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
  users:
    - name: postgres
      databases:
        - thingsboard_mqtt_broker
  backups:
    pgbackrest:
      repos:
        - name: repo1
          volume:
            volumeClaimSpec:
              accessModes: ["ReadWriteOnce"]
              resources:
                requests:
                  storage: 10Gi
EOF
```

Wait for the database pod. PGO creates it a few seconds after the manifest is applied, so the first command waits for
the pod to exist:

```bash
until kubectl get pod -n tbmq -l postgres-operator.crunchydata.com/data=postgres 2>/dev/null | grep -q tbmq-db; do sleep 3; done
kubectl wait --for=condition=Ready pod -l postgres-operator.crunchydata.com/data=postgres \
  -n tbmq --timeout=300s
```

PGO serves the database at `tbmq-db-primary:5432` and stores the generated password in the Secret
`tbmq-db-pguser-postgres`, key `password`.

### Kafka

Install the Strimzi operator and wait for it:

```bash
helm repo add strimzi https://strimzi.io/charts/
helm repo update
helm install strimzi strimzi/strimzi-kafka-operator --version 0.50.0 -n tbmq
kubectl wait --for=condition=Ready pod -l name=strimzi-cluster-operator -n tbmq --timeout=180s
```

Create a three-node Kafka 4.0 cluster in KRaft mode:

```bash
cat <<'EOF' | kubectl apply -n tbmq -f -
apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: combined
  labels:
    strimzi.io/cluster: tbmq-kafka
spec:
  replicas: 3
  roles:
    - controller
    - broker
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim
        size: 10Gi
        deleteClaim: false
  resources:
    requests:
      memory: "2Gi"
      cpu: "500m"
    limits:
      memory: "2Gi"
      cpu: "1"
---
apiVersion: kafka.strimzi.io/v1
kind: Kafka
metadata:
  name: tbmq-kafka
  annotations:
    strimzi.io/node-pools: enabled
    strimzi.io/kraft: enabled
spec:
  kafka:
    version: 4.0.0
    metadataVersion: "4.0"
    listeners:
      - name: plain
        port: 9092
        type: internal
        tls: false
    config:
      auto.create.topics.enable: false
      default.replication.factor: 2
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
  entityOperator:
    topicOperator: {}
    userOperator: {}
EOF
```

Wait for the cluster; this takes a few minutes:

```bash
kubectl wait kafka/tbmq-kafka --for=condition=Ready -n tbmq --timeout=600s
```

Kafka is reachable at `tbmq-kafka-kafka-bootstrap:9092`.

### Valkey

Install a standalone Valkey without a password and wait for it:

```bash
helm repo add valkey https://valkey.io/valkey-helm/
helm repo update
helm install valkey valkey/valkey --version 0.9.3 -n tbmq
kubectl wait --for=condition=Ready pod -l app.kubernetes.io/name=valkey -n tbmq --timeout=180s
```

Valkey is reachable at `valkey:6379`.

### Use Google Cloud managed services

To use Cloud SQL for PostgreSQL, Managed Service for Apache Kafka, and Memorystore for Valkey instead of the in-cluster
deployments, create them in the cluster's region and VPC network, as described in
<DocLink product={props.product} path="installation/cluster/gcp-cluster-setup/#create-the-google-cloud-managed-services" bold={false}>Create the Google Cloud managed services</DocLink>
of the GCP cluster setup guide. Enable the APIs they need first, as listed in its
<DocLink product={props.product} path="installation/cluster/gcp-cluster-setup/#configure-gcp-tools" bold={false}>Configure GCP tools</DocLink> section.
The commands there read the environment variables you defined above.

Once the services are ready, get their addresses: the Cloud SQL private IP address, the Kafka bootstrap address, and
the Memorystore endpoints:

```bash
gcloud sql instances describe $TB_DATABASE_NAME --format="value(ipAddresses[0].ipAddress)"
gcloud managed-kafka clusters describe $TB_KAFKA_NAME --location=$GCP_REGION --format="value(bootstrapAddress)"
gcloud memorystore instances describe $TB_VALKEY_NAME --location=$GCP_REGION \
  --flatten="endpoints[].connections[]" \
  --format="table(endpoints.connections.pscAutoConnection.connectionType:label=TYPE,endpoints.connections.pscAutoConnection.ipAddress:label=ADDRESS)"
```

TBMQ connects to the Memorystore `CONNECTION_TYPE_DISCOVERY` address.

Create the PostgreSQL password Secret in the `tbmq` namespace:

```bash
kubectl create secret generic tbmq-db-secret -n tbmq --from-literal=password='YOUR_DB_PASSWORD'
```

## Modify default chart values

Export the chart's default values to a `values.yaml` file:

```bash
helm show values tbmq-helm-chart/tbmq-cluster > values.yaml
```

The file pins the chart defaults, including the TBMQ image tags. Keep it: you edit and reuse it on every upgrade.

<Aside>
  Do not set `installation.installDbSchema` in `values.yaml`. It creates the database schema and is needed only on the
  first install, so the install command passes it with `--set`.
</Aside>

### Connect to dependencies

In `values.yaml`, find the `postgresql`, `kafka`, and `redis` sections and set these keys to point at the services from
the previous section:

```yaml
postgresql:
  host: "tbmq-db-primary"
  port: 5432
  database: "thingsboard_mqtt_broker"
  username: "postgres"
  existingSecret: "tbmq-db-pguser-postgres"
  existingSecretPasswordKey: "password"

kafka:
  bootstrapServers: "tbmq-kafka-kafka-bootstrap:9092"

redis:
  connectionType: "standalone"
  host: "valkey"
  port: 6379
  usePassword: false
```

`redis.connectionType` defaults to `cluster`, so change it for a single Valkey node.

If you use Google Cloud managed services, set the `postgresql`, `kafka`, and `redis` values from
[Use Google Cloud managed services](#use-google-cloud-managed-services) instead, and add the Kafka topic settings from
the same section to `customEnv` of the `tbmq` and `tbmq-ie` sections. Without the topic settings, the broker nodes don't
start.

### Load balancer configuration

Set the load balancer type to `gcp`:

```yaml
loadbalancer:
  type: "gcp"
```

The chart then creates two internet-facing load balancers through GKE:

| Load balancer                     | Kubernetes resource               | Ports                                                                                              |
|-----------------------------------|-----------------------------------|----------------------------------------------------------------------------------------------------|
| Application Load Balancer         | Ingress `my-tbmq-cluster-http-lb` | `80` (HTTP); `443` (HTTPS) with HTTPS enabled                                                      |
| Passthrough Network Load Balancer | Service `my-tbmq-cluster-mqtt-lb` | `1883` (MQTT), `8084` (MQTT over WebSockets), `8883` (MQTTS), `8085` (MQTT over secure WebSockets) |

The Network Load Balancer passes TCP through to TBMQ unchanged, so it can't terminate TLS. MQTTS and secure WebSockets
work once TBMQ terminates TLS itself, with [mutual TLS](#mqtts-access).

#### HTTPS access

The Application Load Balancer serves HTTPS with a
<a href="https://docs.cloud.google.com/kubernetes-engine/docs/how-to/managed-certs" target="_blank" rel="noopener noreferrer">Google-managed certificate</a>
for your domain. Reserve a global static IP address and print it:

```bash
gcloud compute addresses create tbmq-http-lb-address --global
gcloud compute addresses describe tbmq-http-lb-address --global --format="value(address)"
```

Point your domain at the address with a DNS `A` record. Then enable HTTPS in `values.yaml`:

```yaml
loadbalancer:
  type: "gcp"
  http:
    enabled: true
    ssl:
      enabled: true
      certificateRef: "tbmq-managed-cert"
      domains:
        - "{your-domain}"
      staticIP: "tbmq-http-lb-address"
```

The chart creates a `ManagedCertificate` named after `certificateRef` for the listed domains, assigns the static IP
address to the load balancer, and redirects HTTP on `80` to HTTPS. The certificate is issued once the domain resolves
to the address, which can take up to 60 minutes. After installing, its status turns `Active`:

```bash
kubectl describe managedcertificate tbmq-managed-cert -n tbmq
```

#### MQTTS access

With mutual TLS, the Network Load Balancer forwards ports `8883` and `8085` unchanged, and TBMQ terminates TLS itself.
This also supports
<DocLink product={props.product} path="security/authentication/x509" bold={false}>X.509 certificate authentication</DocLink>.

Create a Secret with the server certificate chain and its private key, in PEM format:

```bash
kubectl create secret generic tbmq-mqtts -n tbmq \
  --from-file=server.pem=server-chain.pem \
  --from-file=mqttserver_key.pem=server.key
```

Enable mutual TLS in `values.yaml`:

```yaml
loadbalancer:
  type: "gcp"
  mqtt:
    enabled: true
    mutualTls:
      enabled: true
      existingSecretName: "tbmq-mqtts"
```

This enables MQTTS on `8883`. To also serve MQTT over secure WebSockets on `8085` with the same certificate, add to
`customEnv` of the `tbmq` section:

```yaml
tbmq:
  customEnv:
    LISTENER_WSS_ENABLED: "true"
    LISTENER_WSS_PEM_CERT: "/ssl-config/server.pem"
    LISTENER_WSS_PEM_KEY: "/ssl-config/mqttserver_key.pem"
```

For a password-protected key and the other options, see
<a href="https://artifacthub.io/packages/helm/tbmq-helm-chart/tbmq-cluster#mutual-tls-mtls-for-mqtt" target="_blank" rel="noopener noreferrer">mutual TLS</a>
in the chart documentation.

## Install the TBMQ Helm chart

From the directory with your `values.yaml`, install the chart:

```bash
helm install my-tbmq-cluster tbmq-helm-chart/tbmq-cluster -n tbmq \
  -f values.yaml \
  --set installation.installDbSchema=true
```

`my-tbmq-cluster` is the Helm release name. It prefixes every resource the chart creates, and later `helm` commands
refer to it.

Helm runs a one-time install pod that creates the database schema and returns when the pod succeeds, usually within a
minute:

```text
NAME: my-tbmq-cluster
NAMESPACE: tbmq
STATUS: deployed
REVISION: 1
...
```

The broker pods start after the schema exists. Wait until they are ready:

```bash
kubectl rollout status statefulset/my-tbmq-cluster-tbmq-node -n tbmq --timeout=600s
```

## Validate HTTP access

Get the address of the Application Load Balancer:

```bash
kubectl get ingress my-tbmq-cluster-http-lb -n tbmq
```

```text
NAME                      CLASS    HOSTS   ADDRESS          PORTS   AGE
my-tbmq-cluster-http-lb   <none>   *       34.144.233.246   80      5m
```

The load balancer takes a few minutes to provision, and its address answers with `404` or `502` errors until the
health checks pass. Then open `http://{ADDRESS}` in your browser, or your domain over HTTPS if you enabled it, and sign
in as System Administrator:

```text title="Username"
sysadmin@thingsboard.org
```

```text title="Password"
sysadmin
```

Change the password after the first sign-in.

## Validate MQTT access

Get the address of the Network Load Balancer:

```bash
kubectl get svc my-tbmq-cluster-mqtt-lb -n tbmq
```

```text
NAME                      TYPE           CLUSTER-IP       EXTERNAL-IP     PORT(S)                                                       AGE
my-tbmq-cluster-mqtt-lb   LoadBalancer   34.118.239.54    104.198.132.85  1883:32017/TCP,8084:32121/TCP,8883:32276/TCP,8085:31926/TCP   5m
```

MQTT clients connect to `EXTERNAL-IP` on port `1883`, and MQTT over WebSockets on port `8084`.

To check the broker end to end, publish and subscribe with the
<a href="https://mosquitto.org/download/" target="_blank" rel="noopener noreferrer">Mosquitto clients</a>. A new
installation has one MQTT credential, **TBMQ WebSockets MQTT Credentials**: username `tbmq_websockets_username` and no
password. In one terminal, subscribe:

```bash
mosquitto_sub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/#' -v -q 1
```

In another, publish:

```bash
mosquitto_pub -h {EXTERNAL-IP} -p 1883 -u tbmq_websockets_username -t 'tbmq/demo/hello' -m 'hello from gke' -q 1
```

The subscriber prints `tbmq/demo/hello hello from gke`. A client that connects without a username is refused as not
authorized, because MQTT Basic authentication is enabled by default. To create your own credentials, see
<DocLink product={props.product} path="user-guide/ui/mqtt-client-credentials" bold={false}>MQTT client credentials</DocLink>.

## Troubleshooting

List the TBMQ pods:

```bash
kubectl get pods -n tbmq -l 'app in (my-tbmq-cluster-tbmq-node,my-tbmq-cluster-tbmq-ie,install-job)'
```

View the logs of a broker node:

```bash
kubectl logs -f my-tbmq-cluster-tbmq-node-0 -n tbmq
```

If `helm install` fails with `failed post-install`, the schema install did not succeed. Read the install pod's logs:

```bash
kubectl logs my-tbmq-cluster-install-pod -n tbmq
```

If applying the Kafka manifest fails with `no matches for kind "KafkaNodePool" in version "kafka.strimzi.io/v1"`, the
cluster has the resource definitions of an older Strimzi release, which `helm install` doesn't upgrade. Replace them
with the definitions of Strimzi 0.50.0, then apply the manifest again:

```bash
kubectl apply --server-side --force-conflicts \
  -f https://github.com/strimzi/strimzi-kafka-operator/releases/download/0.50.0/strimzi-crds-0.50.0.yaml
```

Broker pods that stay in `Init:0/1` are waiting for the schema. For the common causes and fixes, see
<a href="https://artifacthub.io/packages/helm/tbmq-helm-chart/tbmq-cluster#troubleshooting-the-install" target="_blank" rel="noopener noreferrer">Troubleshooting the install</a>
in the chart documentation.

With Managed Kafka, `SaslAuthenticationException` in the broker logs means the `tbmq-kafka-credentials` Secret or the
service account's `roles/managedkafka.client` role is wrong; `Invalid JWT Signature` means the Secret holds a key that
was deleted. After you fix the Secret, restart the pods:

```bash
kubectl rollout restart statefulset/my-tbmq-cluster-tbmq-node statefulset/my-tbmq-cluster-tbmq-ie -n tbmq
```

If the Ingress `ADDRESS` or the Service `EXTERNAL-IP` stays empty, its events give the reason:

```bash
kubectl describe ingress my-tbmq-cluster-http-lb -n tbmq
kubectl describe svc my-tbmq-cluster-mqtt-lb -n tbmq
```

- **The Ingress has no events at all:** GKE ignores it. Charts before 2.3.2 select the controller with
  `ingressClassName: gce`, which matches no IngressClass on GKE. Upgrade the release to chart 2.3.2 or later.
- **`Error syncing to GCP` for a `networkEndpointGroups` resource named `...-kube-system-default-http-backend-...`:**
  GKE deleted the default backend's network endpoint group along with the cluster's previous Ingress, for example
  after you uninstalled and reinstalled the release. GKE recreates it, and the address appears within about 10 minutes.

## Upgrading

Back up your PostgreSQL database before upgrading. Then review the
<DocLink product={props.product} path="installation/upgrade-instructions" bold={false}>upgrade instructions</DocLink>
for the notes on every version between yours and the target.

<Aside type="note">
  Review the behavior changes in the <DocLink product={props.product} path="releases/#v242-november-25-2026">2.4.2 release notes</DocLink> before upgrading to v2.4.2.
  If SCRAM is the only enabled authentication provider, TBMQ now refuses clients that send no MQTT 5 Authentication Method instead of accepting them without credentials —
  <DocLink product={props.product} path="security/authentication/scram/#accept-only-scram-clients" bold={false}>move every client to SCRAM</DocLink> first.
  If a Kafka integration has **Send only message payload** on, a payload that is not valid UTF-8 is now sent as raw bytes instead of Base64 —
  <DocLink product={props.product} path="integrations/kafka/#configuration" bold={false}>update the consumers</DocLink> that decode it.
  A `value.serializer` set in **Other properties** is now ignored for every Kafka integration: record values are always sent as bytes.
</Aside>

<Aside type="note">
  Review the behavior changes in the <DocLink product={props.product} path="releases/#v241-october-8-2026">2.4.1 release notes</DocLink> before upgrading to v2.4.1.
  If you set `MQTT_TOPIC_MAX_SEGMENTS_COUNT`, raise it by 1 to keep the previous limit — the limit now counts topic segments instead of `/` delimiters.
</Aside>

<Aside type="note">
  If you scrape TBMQ metrics, review the <DocLink product={props.product} path="releases/#v240-august-27-2026">2.4.0 release notes</DocLink> before upgrading to v2.4.0.
  Several Prometheus metric and tag names changed, so queries, recording rules, alerts and dashboards need updating.
</Aside>

<ShowFor product={props.product} show={[Products.TBMQ_PE]}>

<ConditionalHeading level={3} id="upgrade-from-ce-to-pe" showFor="mqtt-broker-pe">Upgrade from TBMQ to TBMQ PE</ConditionalHeading>

To move a Community Edition release to PE, first upgrade it to the same TBMQ version as the target PE release. Then:

<Steps>

1. **Switch `values.yaml` to PE.**

   In the `values.yaml` of your CE release, set the PE images and the license exactly as for a fresh PE install: see
   [Configure license and broker images](#configure-license-and-broker-images), including the license Secret.

2. **Stop TBMQ.**

   Scale the broker and Integration Executor to zero so nothing uses the database while it is migrated:

   ```bash
   kubectl scale statefulset/my-tbmq-cluster-tbmq-node --replicas=0 -n tbmq
   kubectl scale statefulset/my-tbmq-cluster-tbmq-ie --replicas=0 -n tbmq
   ```

3. **Run the upgrade.**

   ```bash
   helm upgrade my-tbmq-cluster tbmq-helm-chart/tbmq-cluster -n tbmq \
     -f values.yaml \
     --set upgrade.upgradeDbSchema=true \
     --set upgrade.fromVersion=ce
   ```

   The migration converts the database to PE, then Helm starts the broker and Integration Executor on the PE images
   with their usual replica count.

</Steps>

Pass `upgrade.fromVersion=ce` only for this migration. On later PE upgrades, leave it out: with it, the migration fails.

</ShowFor>

### Run upgrade

<Steps>

1. **Update the chart repository.**

   ```bash
   helm repo update
   ```

2. **Compare versions.**

   The `APP VERSION` column is the TBMQ version. Compare your release with the latest chart:

   ```bash
   helm list -n tbmq
   helm search repo tbmq-helm-chart/tbmq-cluster
   ```

3. **Update `values.yaml`.**

   Export the new defaults and compare them with your file:

   ```bash
   helm show values tbmq-helm-chart/tbmq-cluster > values-new.yaml
   diff values.yaml values-new.yaml
   ```

   Carry the changes you need into `values.yaml`. Always update the image tags, or the release keeps running the old
   TBMQ version:

   <Code code={props.product === Products.TBMQ_PE ? peTagsYaml : ceTagsYaml} lang="yaml" />

4. **Run the upgrade.**

   ```bash
   helm upgrade my-tbmq-cluster tbmq-helm-chart/tbmq-cluster -n tbmq \
     -f values.yaml \
     --set upgrade.upgradeDbSchema=true
   ```

   A pre-upgrade job migrates the database, then Kubernetes replaces the TBMQ pods one at a time, each after the
   previous one is ready. Wait for it to finish:

   ```bash
   kubectl rollout status statefulset/my-tbmq-cluster-tbmq-node -n tbmq --timeout=600s
   ```

</Steps>

If the `APP VERSION` doesn't change, there is nothing to migrate: run the same `helm upgrade` without
`--set upgrade.upgradeDbSchema=true`. With it, the migration fails with `database already upgraded to current version`
and the release is marked `failed`; running the upgrade again without the flag fixes it.

<Aside title="Upgrades that stop TBMQ">
  Upgrades to 2.4.0 and later are rolling upgrades: Kubernetes replaces the TBMQ pods one at a time, so the cluster keeps
  accepting connections. Upgrades to 2.3.0 and earlier must stop every TBMQ node while the database is migrated — see
  the <DocLink product={props.product} path="installation/upgrade-instructions/#downtime" bold={false}>downtime of each version</DocLink>.
  For those, scale the TBMQ pods to zero before `helm upgrade`; Helm starts them again:

  ```bash
  kubectl scale statefulset/my-tbmq-cluster-tbmq-node --replicas=0 -n tbmq
  kubectl scale statefulset/my-tbmq-cluster-tbmq-ie --replicas=0 -n tbmq
  ```
</Aside>

<Aside type="tip">
  To upgrade to a specific version, add `--version {chart-version}` to `helm show values` and `helm upgrade`.
  `helm search repo tbmq-helm-chart/tbmq-cluster --versions` lists each chart version with its TBMQ version.
  TBMQ versions must be upgraded one at a time: if you are more than one version behind, run the upgrade once for each
  TBMQ version in between, with the chart version for it.
</Aside>

Chart 2.0.0 (TBMQ 2.3.0) removed the PostgreSQL, Kafka, and Redis subcharts that chart 1.x bundled. To upgrade a
release from chart 1.x, follow
<a href="https://github.com/thingsboard/helm-charts/tree/main/tbmq#upgrading-from-chart-version-1x-to-200-tbmq-220--230" target="_blank" rel="noopener noreferrer">Upgrading from chart version 1.x to 2.0.0</a>
in the chart documentation.

## Uninstalling TBMQ Helm chart

```bash
helm uninstall my-tbmq-cluster -n tbmq
```

This removes the TBMQ resources of the release, and GKE deletes the two load balancers. It keeps the broker's data
volumes; delete them with:

```bash
kubectl delete pvc -n tbmq -l app=my-tbmq-cluster-tbmq-node
```

PostgreSQL, Kafka, and Valkey keep running, and so do the Secrets you created.

To remove the in-cluster dependencies too, delete the database and Kafka clusters while their operators still run,
then the operators, Valkey, and the namespace:

```bash
kubectl delete postgrescluster tbmq-db -n tbmq
kubectl delete kafka tbmq-kafka -n tbmq
kubectl delete kafkanodepool combined -n tbmq
helm uninstall valkey strimzi pgo -n tbmq
kubectl delete namespace tbmq
```

Deleting the namespace first leaves it stuck in `Terminating`: the operators are removed before they can clean up their
clusters. Deleting the namespace also deletes the remaining volumes and their disks.

If you use Google Cloud managed services, delete only the namespace:

```bash
kubectl delete namespace tbmq
```

The managed services aren't affected; [Delete the GKE cluster](#delete-the-gke-cluster) covers them.

## Delete the GKE cluster

<Steps>

1. **Uninstall TBMQ and its dependencies**, as in the previous section.

2. **Wait for the load balancers to go.** GKE deletes them once the Ingress and the Service are gone. A load balancer
   that still exists when the cluster is deleted is left behind. Wait until this command lists nothing:

   ```bash
   gcloud compute forwarding-rules list --filter="description~tbmq/my-tbmq-cluster" --format="table(name,IPAddress)"
   ```

3. **Delete the GKE cluster.**

   ```bash
   gcloud container clusters delete $TB_CLUSTER_NAME --region=$GCP_REGION
   ```

   The deletion takes about 10 minutes.

4. **Delete the HTTPS static IP address**, if you reserved one:

   ```bash
   gcloud compute addresses delete tbmq-http-lb-address --global
   ```

5. **Delete the Google Cloud managed services**, if you use them: the instances, the Kafka service account and its
   key, and the network resources you created for them. Follow the **Delete the managed services**, **Delete the Kafka
   service account and its role binding**, and **Delete the network resources you created for this guide** steps of
   <DocLink product={props.product} path="installation/cluster/gcp-cluster-setup/#cluster-deletion" bold={false}>Cluster deletion</DocLink>
   in the GCP cluster setup guide.

</Steps>
