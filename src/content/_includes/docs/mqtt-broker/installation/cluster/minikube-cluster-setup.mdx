This guide covers setting up TBMQ in cluster mode using Minikube.

The scripts deploy two TBMQ nodes, an Integration Executor, PostgreSQL, Kafka, and Valkey into the
`thingsboard-mqtt-broker` namespace. The TBMQ service is exposed on these node ports of the Minikube IP:

| Port    | Protocol             | Used for                                                                    |
| ------- | -------------------- | --------------------------------------------------------------------------- |
| `30001` | HTTP                 | TBMQ UI and REST API                                                        |
| `30002` | MQTT                 | MQTT clients                                                                |
| `30003` | MQTTS                | MQTT clients that connect over TLS, once you enable the TBMQ SSL listener (`LISTENER_SSL_ENABLED`) |
| `30004` | MQTT over WebSockets | MQTT clients that connect over WebSockets                                   |

## Prerequisites

- <a href="https://minikube.sigs.k8s.io/docs/start/" target="_blank" rel="noopener noreferrer">Minikube</a> and
  <a href="https://kubernetes.io/docs/tasks/tools/" target="_blank" rel="noopener noreferrer">kubectl</a> installed,
  and a running Minikube cluster:

  ```bash
  minikube start
  ```

- Git installed.

<Aside type="caution" title="Check the kubectl context">
  The scripts run against your current kubectl context and set its default namespace to `thingsboard-mqtt-broker`.
  `minikube start` switches the context to Minikube; if you changed it since, switch back before running the scripts.
  This command must print `minikube`:

  ```bash
  kubectl config current-context
  ```
</Aside>

## Running

<Steps>

1. **Deploy TBMQ.**

   ```bash
   ./k8s-deploy-tbmq.sh
   ```

   The TBMQ nodes start one after another, so the deployment can take a few minutes. All pods are ready when every row
   of `kubectl get pods` shows `1/1` in the **READY** column.

2. **Open the UI.**

   Get the Minikube IP:

   ```bash
   minikube ip
   ```

   Open `http://{minikube-ip}:30001` in your browser (e.g., **http://192.168.49.2:30001**). You should see the TBMQ
   login page. MQTT clients connect to the same IP on port `30002`.

   <Aside title="Docker driver on macOS or Windows">
     With the Docker driver on macOS or Windows, the Minikube IP is not reachable from the host. Run
     `minikube service tbmq -n thingsboard-mqtt-broker --url` and use the addresses it prints instead; keep the
     command running while you use them. See
     <a href="https://minikube.sigs.k8s.io/docs/handbook/accessing/" target="_blank" rel="noopener noreferrer">Accessing apps</a>
     for details.
   </Aside>

3. **Sign in as System Administrator.**

   Use the default **System Administrator** credentials:

   ```text title="Username"
   sysadmin@thingsboard.org
   ```

   ```text title="Password"
   sysadmin
   ```

4. **Change the default password.**

   On first login, you are prompted to change the default password and re-login with the new credentials.

</Steps>

## Logs, delete, and redeploy commands

The scripts create these pods: `tbmq-0` and `tbmq-1` (TBMQ nodes), `tbmq-integration-executor-0`, `postgres-…`,
`tbmq-kafka-0`, and `tbmq-valkey-…`.

```bash title="View TBMQ node logs"
kubectl logs -f tbmq-0
```

```bash title="View the state of the pods, services, deployments, and statefulsets"
kubectl get pods
kubectl get services
kubectl get deployments
kubectl get statefulsets
```

See the <a href="https://kubernetes.io/docs/reference/kubectl/quick-reference/" target="_blank" rel="noopener noreferrer">kubectl Quick Reference</a> for more details.

```bash title="Delete the TBMQ nodes and the Integration Executor"
./k8s-delete-tbmq.sh
```

PostgreSQL, Kafka, and Valkey keep running, and the data stays. `./k8s-deploy-tbmq.sh` brings the TBMQ nodes and the
Integration Executor back.

```bash title="Delete all resources, including the databases (deletes all data)"
./k8s-delete-all.sh
```

<Aside type="tip">

CE-to-PE migration is supported for the **same version only**.
If you are on an earlier CE version,
<DocLink product={Products.TBMQ} path="installation/upgrade-instructions/">upgrade TBMQ CE</DocLink> to the latest version first.
For all supported paths, see the
<DocLink product={props.product} path="installation/upgrade-instructions/#upgrade-from-tbmq-to-tbmq-pe">upgrade instructions</DocLink>.

TBMQ PE uses its own repository, so the migration moves your deployment from the TBMQ `tbmq/k8s/minikube` directory to
the PE `tbmq-pe-k8s/minikube` directory. PostgreSQL, Kafka, Valkey, and their data stay the same.

<Steps>

1. **Clone the TBMQ PE repository.**

   Clone it next to your TBMQ directory, as described in [Clone TBMQ K8S repository](#clone-tbmq-pe-repository).

2. **Carry over your settings.**

   Copy your own changes from the TBMQ directory into the matching PE files, such as `tbmq.yml`,
   `tbmq-configmap.yml`, and `tbmq-ie.yml`. Keep the PE image names and the license settings in the PE `tbmq.yml`.

3. **Create the license secret.**

   Create the `tbmq-license` secret as described in [Configure the license key](#configure-the-license-key).

4. **Delete the TBMQ nodes.**

   In the TBMQ `tbmq/k8s/minikube` directory, run:

   ```bash
   ./k8s-delete-tbmq.sh
   ```

   The PE `tbmq` statefulset adds a volume for the license data, which Kubernetes can't add to an existing statefulset,
   so the TBMQ one must be deleted first. PostgreSQL, Kafka, and Valkey keep running.

5. **Migrate the database and deploy TBMQ PE.**

   In the PE `tbmq-pe-k8s/minikube` directory, run:

</Steps>

### Run upgrade

<Steps>

1. **Switch to the new release branch.**

   <Code code={switchBranchCmd} lang="bash" />

   `git checkout -m` switches to the release branch and keeps your own edits to files such as `tbmq.yml` and
   `tbmq-configmap.yml`. Make sure the TBMQ images in `tbmq.yml`, `tbmq-ie.yml`, and `database-setup.yml` use the
   target version (e.g., **{TBMQ_VER}**).

   <Aside type="caution" title="Check for conflicts">
     If one of your edits overlaps a change in the release, Git keeps both versions in that file between `<<<<<<<`
     and `>>>>>>>` markers and lists the file as `UU` in `git status`. Edit the file to keep the lines you need and
     remove the markers, then run `git add` with the file name.
   </Aside>

2. **Run the upgrade.**

   <Code code={upgradeCmds} lang="bash" />

   `k8s-upgrade-tbmq.sh` upgrades the database but does not touch the TBMQ pods — they keep running the previous image
   until `k8s-deploy-tbmq.sh` applies the updated manifests. Kubernetes then replaces the TBMQ pods one at a time, each
   after the previous one is ready.

</Steps>

<Aside title="Upgrades that stop TBMQ">
  Upgrades to 2.4.0 and later are rolling upgrades: Kubernetes replaces the TBMQ pods one at a time, so the cluster keeps
  accepting connections. Upgrades to 2.3.0 and earlier must stop every TBMQ node while the database is migrated — see
  the <DocLink product={props.product} path="installation/upgrade-instructions/#downtime" bold={false}>downtime of each version</DocLink>.
  For those, delete the TBMQ pods before the database upgrade:

  <Code code={`./k8s-delete-tbmq.sh\n./k8s-upgrade-tbmq.sh\n./k8s-deploy-tbmq.sh`} lang="bash" />

  MQTT clients can't connect from the first command until the new pods are ready.
</Aside>

<Aside type="tip">
  To upgrade to a specific version (e.g., v2.0.0), replace the branch in the commands above with the target branch
  name, e.g., `release-2.0.0`.
</Aside>
