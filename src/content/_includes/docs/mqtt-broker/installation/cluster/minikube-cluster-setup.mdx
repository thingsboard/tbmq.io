## Running

Deploy TBMQ:

```bash
./k8s-deploy-tbmq.sh
```

Once all resources have started, open `http://{your-cluster-ip}:30001` in your browser (e.g. **http://192.168.49.2:30001**).
Check your cluster IP with:

```bash
minikube ip
```

You should see the TBMQ login page. Use the default **System Administrator** credentials:

**Username:**

```
sysadmin@thingsboard.org
```

**Password:**

```
sysadmin
```

On first login, you are prompted to change the default password and re-login with the new credentials.

## Logs, delete statefulsets and services

To view TBMQ node logs:

1. List running TBMQ pods:

   ```bash
   kubectl get pods -l app=tbmq
   ```

2. Fetch logs for a specific pod:

   ```bash
   kubectl logs -f TBMQ_POD_NAME
   ```

   Where `TBMQ_POD_NAME` is the pod name from the list above.

To check the state of all pods, services, deployments, and statefulsets:

```bash
kubectl get pods
kubectl get services
kubectl get deployments
kubectl get statefulsets
```

See the <a href="https://kubernetes.io/docs/reference/kubectl/cheatsheet/" target="_blank" rel="noopener noreferrer">kubectl Cheat Sheet</a> for more details.

To delete TBMQ nodes:

```bash
./k8s-delete-tbmq.sh
```

To delete all resources including databases:

```bash
./k8s-delete-all.sh
```

<details>
<summary>This release migrates MQTT authentication from YAML/env configuration into the database.</summary>

The upgrade script reads from **`database-setup.yml`**. Variables from `tb-broker.yml` are
**not** applied during the upgrade — only the values in
`database-setup.yml` are used. Ensure this file reflects your active configuration.

<Aside type="tip">
  If you use only Basic authentication, set `SECURITY_MQTT_SSL_ENABLED=false`.
  If you use only X.509 authentication, set `SECURITY_MQTT_BASIC_ENABLED=false` and `SECURITY_MQTT_SSL_ENABLED=true`.
</Aside>

**Supported variables in database-setup.yml**

- `SECURITY_MQTT_BASIC_ENABLED` (`true|false`)
- `SECURITY_MQTT_SSL_ENABLED` (`true|false`)
- `SECURITY_MQTT_SSL_SKIP_VALIDITY_CHECK_FOR_CLIENT_CERT` (`true|false`) — usually `false`

Once the file is verified, proceed with the [upgrade](#run-upgrade).

</details>

### Run upgrade

Pull the latest changes from the release branch:

<Code code={gitPullCmd} lang="bash" />

<Aside type="tip">
  To upgrade to a specific version (e.g. v2.0.0), replace the branch with the target branch name, e.g. `release-2.0.0`.
</Aside>

**Note:** Make sure any custom changes are not lost during the merge.

<Aside>
If you encounter conflicts during the merge that are unrelated to your changes, accept all remote changes:

1. Abort the current merge: `git merge --abort`
2. Re-pull accepting remote changes: <code>git pull origin {TBMQ_BRANCH} -X theirs</code>

Merge strategy options:

- `-X ours` — auto-resolve conflicts by favoring your local version
- `-X theirs` — auto-resolve conflicts by favoring the remote version
</Aside>

After pulling, run the upgrade script:

```bash
./k8s-upgrade-tbmq.sh
```

<Aside>
You may optionally stop TBMQ pods before running the database upgrade to ensure a consistent DB state:

<Code code="./k8s-delete-tbmq.sh" lang="bash" />

This causes downtime, but most upgrades do not require stopping TBMQ. Once the upgrade completes, redeploy to roll out the new version:

<Code code="./k8s-deploy-tbmq.sh" lang="bash" />
</Aside>
