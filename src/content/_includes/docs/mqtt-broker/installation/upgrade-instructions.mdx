TBMQ upgrades one release at a time. Each upgrade migrates the PostgreSQL database to the new version and restarts
TBMQ on the new image; some releases also need manual changes first.

## Before you upgrade

1. **Find your current version.** Log in to the TBMQ UI: the **Version** card on the **Home** page shows the
   deployed version under **Current**.

   To confirm which version the database is on, run this against the TBMQ database:

   <Code code={schemaVersionQuery} lang="sql" />

   The result encodes the version as `major × 1000000 + minor × 1000 + patch`. For example, `2004000` is 2.4.0.

2. **Back up PostgreSQL**, for example with `pg_dump`, or with your managed database's snapshots.

3. **Read the notes for every release between your version and the target**, not only the last one. Some releases
   need changes before the upgrade runs, and each note says whether you must
   [stop TBMQ or can upgrade without downtime](#downtime).

## Downtime

Every version note says which of two kinds of upgrade it is:

- <Badge text="Stop TBMQ" variant="danger" class="nowrap-badge" /> — stop every TBMQ node before the upgrade migrates the database, then
  start them on the new version. MQTT clients cannot connect until the nodes are back.
- <Badge text="Rolling upgrade" variant="success" class="nowrap-badge" /> — the database is migrated while the old nodes keep running, then
  the nodes are replaced one at a time. The cluster keeps accepting connections: clients on the node being replaced are
  disconnected, and when they reconnect, the load balancer sends them to a running node.

A rolling upgrade needs at least two TBMQ nodes and a deployment that replaces them one by one:

| Deployment                                     | Rolling upgrade                                                                                                 |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Docker (Linux, macOS, Windows)                 | No — a single node, so clients are disconnected while it restarts                                               |
| Docker Compose cluster                         | No — its upgrade procedure stops every node; clients can reconnect once the cluster is back |
| Kubernetes scripts (Minikube, AWS, Azure, GCP) | Yes — pods are replaced one at a time, each only after the previous one is ready |
| Helm                                           | Yes — same one-at-a-time pod replacement                                                                        |

The Kubernetes manifests and the Helm chart run two TBMQ nodes by default. If you need upgrades without downtime, deploy
on Kubernetes or Helm.

<ConditionalHeading level={3} id="upgrading-to-241" exclude="mqtt-broker-pe">Upgrading to 2.4.1</ConditionalHeading>

**From 2.4.0.** The upgrade only records the new schema version — no table is created or altered, and no data is
migrated.

**Downtime:** <Badge text="Rolling upgrade" variant="success" class="nowrap-badge" /> on deployments that [support it](#downtime).

**Check before upgrading:** `MQTT_TOPIC_MAX_SEGMENTS_COUNT` now counts topic segments instead of `/` delimiters. If you
set it, raise it by 1 to keep the previous limit. The default `0` (no limit) is unaffected. See the
<DocLink product={props.product} path="releases/#v241-october-8-2026" bold={false}>2.4.1 release notes</DocLink> for the
other behavior changes.

<ConditionalHeading level={3} id="upgrading-to-240" exclude="mqtt-broker-pe">Upgrading to 2.4.0</ConditionalHeading>

**From 2.3.0.** The upgrade only records the new schema version — no table is created or altered, and no data is
migrated.

**Downtime:** <Badge text="Rolling upgrade" variant="success" class="nowrap-badge" /> on deployments that [support it](#downtime). During a rolling upgrade, don't create, edit or delete integrations until every TBMQ node runs 2.4.0: 2.3.0
nodes ignore the integration change notifications that 2.4.0 nodes send.

**Check before upgrading:** if you scrape TBMQ metrics, several Prometheus metric and tag names changed, so queries,
recording rules, alerts and dashboards need updating. The
<DocLink product={props.product} path="releases/#v240-august-27-2026" bold={false}>2.4.0 release notes</DocLink> list
them.

<ConditionalHeading level={3} id="upgrading-to-230" exclude="mqtt-broker-pe">Upgrading to 2.3.0</ConditionalHeading>

**From 2.2.0.** This release replaces the Bitnami images for third-party components with official open-source images,
in TBMQ's Docker Compose files and Kubernetes manifests alike.

**Downtime:** <Badge text="Stop TBMQ" variant="danger" class="nowrap-badge" /> — stop every TBMQ node before the upgrade.

| Component      | 2.2.0                       | 2.3.0                | What it means for your data                                                                       |
| -------------- | --------------------------- | -------------------- | ------------------------------------------------------------------------------------------------- |
| PostgreSQL     | `postgres:16`               | `postgres:17`        | Major-version upgrade: PostgreSQL 17 cannot open a 16 data directory, so the data must be migrated |
| Kafka          | `bitnamilegacy/kafka:3.7.0` | `apache/kafka:4.0.0` | New data directory — the Bitnami volume cannot be reused                                          |
| Redis → Valkey | `bitnamilegacy/redis:7.2.5` | `valkey/valkey:8.0`  | New data directory and a new volume                                                               |

The TBMQ upgrade migrates only the PostgreSQL schema. It does not upgrade PostgreSQL itself and moves no Kafka or
Redis data. Before running it:

1. **Back up everything you intend to keep:** the PostgreSQL database (for example, with `pg_dump`), and the Kafka and
   Redis volumes if you plan to migrate them.
2. **Upgrade PostgreSQL 16 to 17**, for example with `pg_upgrade` or a dump and restore into a fresh PostgreSQL 17
   instance.
3. **Decide what to do with Kafka and Redis data:** migrate it manually to the new images, or start them on new, empty
   volumes.

<Aside type="caution">
  Empty Kafka and Valkey volumes mean losing client sessions and subscriptions, retained messages, and messages not yet
  delivered to persistent clients. Users, MQTT client credentials and settings live in PostgreSQL and are kept.
</Aside>

These changes follow the long-term plan in the
<a href="https://github.com/thingsboard/thingsboard-ce-k8s/blob/master/BITNAMI-IMAGE-MIGRATION.md#3-long-term-production-solution" target="_blank" rel="noopener noreferrer">Bitnami image migration guide</a>.
<DocLink product={props.product} path="help" bold={false}>Contact us</DocLink> if you need guidance on the migration.

<ConditionalHeading level={3} id="upgrading-to-220" exclude="mqtt-broker-pe">Upgrading to 2.2.0</ConditionalHeading>

**From 2.1.0.** MQTT authentication settings move from YAML and environment variables into the database. The upgrade
creates the authentication providers from these legacy variables, each defaulting to `false`:

- `SECURITY_MQTT_BASIC_ENABLED` — enables the Basic provider
- `SECURITY_MQTT_SSL_ENABLED` — enables the X.509 provider
- `SECURITY_MQTT_SSL_SKIP_VALIDITY_CHECK_FOR_CLIENT_CERT` — usually `false`

**Downtime:** <Badge text="Stop TBMQ" variant="danger" class="nowrap-badge" /> — stop every TBMQ node before the upgrade.

**Do before upgrading:** pass your current values of these variables to the upgrade. Where they go depends on the
deployment, and the deployment guide says which file to set them in.

<Aside type="danger" title="Missing values disable authentication">
  If the upgrade does not receive these variables, it creates the Basic and X.509 providers disabled. With no provider
  enabled, TBMQ accepts every client without authentication. After the upgrade, check **Authentication → Providers** in
  the TBMQ UI and enable the providers you use.
</Aside>

The upgrade also makes MQTT client credential names unique: where two credentials share a name, the later one gets a
random three-character suffix.

<ConditionalHeading level={3} id="upgrading-to-210" exclude="mqtt-broker-pe">Upgrading to 2.1.0</ConditionalHeading>

**From 2.0.0 or 2.0.1.** From this release on, the upgrade detects the source version itself — `fromVersion` is no
longer needed.

**Downtime:** <Badge text="Stop TBMQ" variant="danger" class="nowrap-badge" /> — stop every TBMQ node before the upgrade.

**Do before upgrading:**

- **Add the Integration Executor service.** This release introduces the
  <DocLink product={props.product} path="integrations" bold={false}>Integration Executor</DocLink> microservice; the
  deployment guide shows how to add it.
- **Upgrade the third-party services.** PostgreSQL moves from 15 to 16, a major-version upgrade that needs a data
  migration (`pg_upgrade` or dump and restore). Kafka moves from 3.5.1 to 3.7.0 and Redis from 7.0 to 7.2.5; follow
  each project's upgrade notes.

<ConditionalHeading level={3} id="upgrading-to-200" exclude="mqtt-broker-pe">Upgrading to 2.0.0</ConditionalHeading>

**From 1.4.0**, with `fromVersion` set to `1.4.0`. Redis becomes a required component: TBMQ now stores messages for
persistent DEVICE clients in Redis instead of PostgreSQL, and the upgrade copies the stored messages across. See the
<DocLink product={props.product} path="architecture" bold={false}>architecture</DocLink> for details.

**Downtime:** <Badge text="Stop TBMQ" variant="danger" class="nowrap-badge" /> — stop every TBMQ node before the upgrade.

**Do before upgrading:** back up PostgreSQL. Standalone Docker deployments must also add a Redis service; the Docker
guides show how.

<ConditionalHeading level={2} id="upgrade-from-tbmq-to-tbmq-pe" showFor="mqtt-broker-pe">Upgrade from TBMQ to TBMQ PE</ConditionalHeading>

**Downtime:** <Badge text="Stop TBMQ" variant="danger" class="nowrap-badge" /> — stop every TBMQ node before the upgrade. The migration creates the PE tables and makes a role mandatory for every user

You can migrate from TBMQ to TBMQ PE of the **same version**.
For example, TBMQ {TBMQ_VER} can be upgraded to TBMQ PE {TBMQ_VER}.
Cross-version migration (e.g. TBMQ {TBMQ_PREV_VER} to TBMQ PE {TBMQ_VER}) is **not supported** — upgrade TBMQ to the target version first, then migrate to TBMQ PE.

<Aside type="note">
  To upgrade to TBMQ PE {TBMQ_VER}, you must be running TBMQ {TBMQ_VER} first. If you are still on an earlier version,
  <DocLink product={Products.TBMQ} path="installation/upgrade-instructions/">upgrade TBMQ</DocLink> to {TBMQ_VER} before migrating to TBMQ PE.
</Aside>

<Aside type="tip">
  Starting from v2.3.0, both editions use identical third-party component versions. If you are migrating at v2.3.0 or later, no additional third-party changes are required — proceed directly with the CE-to-PE upgrade script.
</Aside>

<Aside type="tip">
  After the upgrade completes, clear your browser cache to ensure PE assets load correctly.
</Aside>

<ConditionalHeading level={3} id="third-party-component-updates-in-tbmq-pe-v220" showFor="mqtt-broker-pe">Third-party component updates (CE v2.2.0 → PE v2.2.0 only)</ConditionalHeading>

The following changes apply **only** when migrating from TBMQ v2.2.0 to TBMQ PE v2.2.0. They do not apply to v2.3.0 and later.

These updates follow the modernization plan outlined in the <a href="https://github.com/thingsboard/thingsboard-ce-k8s/blob/master/BITNAMI-IMAGE-MIGRATION.md#3-long-term-production-solution" target="_blank" rel="noopener noreferrer">Bitnami Image Migration</a> guide.

| Component            | TBMQ v2.2.0                  | TBMQ PE v2.2.0      | Notes                                                                                       |
| -------------------- | ---------------------------- | ------------------- | ------------------------------------------------------------------------------------------- |
| **PostgreSQL**       | `postgres:16`                | `postgres:17`       | Major-version upgrade: PostgreSQL 17 cannot open a 16 data directory, so the data must be migrated. |
| **Kafka**            | `bitnamilegacy/kafka:3.7.0`  | `apache/kafka:4.0.0` | Migrated from Bitnami to the official Apache Kafka image. New volume paths are required.   |
| **Redis → Valkey** | `bitnamilegacy/redis:7.2.5`  | `valkey/valkey:8.0` | Migrated from Bitnami Redis to Valkey, with a new volume.       |

Before starting, create full backups of your environment — including the PostgreSQL database (for example, using `pg_dump`) and your Kafka and Redis data volumes if you plan to migrate them.

PostgreSQL is upgraded from **16 to 17**. PostgreSQL 17 cannot start on a 16 data directory, so you must migrate the data (for example, using `pg_upgrade` or a dump and restore).

Kafka and Redis have been migrated from Bitnami images to official open-source alternatives. The new images use **different internal data directories and volume mappings**, so existing Bitnami volumes cannot be reused directly. You must either migrate your data manually or start from new, empty volumes.

<Aside type="caution">
  Starting from new volumes removes all data stored in Kafka and Redis, including client session states, undelivered messages, retained messages, and any other persisted broker data.
</Aside>

The standard upgrade script updates only the PostgreSQL database schema and does not include data migration logic for Kafka or Valkey.

<Aside type="note">
  <DocLink product={Products.TBMQ_PE} path="help">Contact us</DocLink> if you need guidance for the migration. We can offer general recommendations to help facilitate a smoother upgrade.
</Aside>

## Troubleshooting

The upgrade validates the database before it changes anything. If a check fails, the upgrade stops without touching the
database; search its output for `Upgrade failed:` and match the message that follows it below.

**`Upgrade failed: database already upgraded to current version.`**

The database is already on the version you are upgrading to, so there is nothing to do — usually because this upgrade
already completed. Start TBMQ on the new version.

**`Upgrade failed: database version 'X' is not supported for upgrade. Supported versions are: [...]`**

The database is on version `X`, but this upgrade accepts only the versions in the list — normally just the release
immediately before the target. Upgrade one release at a time along the supported upgrade paths above, starting
from `X`.

**`Upgrade failed: can't upgrade TBMQ CE database using TBMQ PE.`** (or `… TBMQ PE database using TBMQ CE.`)

The edition you are upgrading with does not match the edition recorded in the database. Use TBMQ to upgrade a TBMQ
database and TBMQ PE to upgrade a TBMQ PE database.

<ShowFor product={props.product} show={[Products.TBMQ_PE]}>
To migrate a TBMQ database to TBMQ PE, run the CE-to-PE upgrade described in
[Upgrade from TBMQ to TBMQ PE](#upgrade-from-tbmq-to-tbmq-pe) — it takes the source edition as an argument, which a
plain upgrade does not.

**`Upgrade failed: transitioning from CE to PE requires the database to first be upgraded to version 'X' using TBMQ CE.`**

A CE-to-PE migration is only supported at the same version. Upgrade TBMQ to the version reported in the message first,
then migrate to TBMQ PE.
</ShowFor>

<ShowFor product={props.product} show={[Products.TBMQ]}>
**`Upgrade failed: can't upgrade TBMQ null database using TBMQ CE.`**

The `tb_schema_settings` table is empty: the upgrade is pointed at the wrong database, or at one that a TBMQ
installation never initialized. Check the database connection settings of the upgrade.

**`Upgrade failed: the database schema version is missing.`**

The `tb_schema_settings` table records an edition but no version, or it is empty and the checks were skipped with
`SKIP_SCHEMA_VERSION_CHECK`. Check that the upgrade points at your TBMQ database.
</ShowFor>

**`Upgrade failed: the database schema version is missing.`**

The `tb_schema_settings` table holds no version: the upgrade is pointed at the wrong database, or at one that a TBMQ

### Forcing a re-upgrade

Setting the `SKIP_SCHEMA_VERSION_CHECK` environment variable to `true` on the upgrade makes it skip **all** of the
validation above and run regardless. Set it where your deployment's upgrade reads its environment:

| Deployment                                | Where to set `SKIP_SCHEMA_VERSION_CHECK=true`                         |
| ----------------------------------------- | --------------------------------------------------------------------- |
| Docker (Linux, macOS, Windows)            | `.tbmq-upgrade.env`, next to `docker-compose.yml`                     |
| Docker Compose cluster                    | `tbmq.env`                                                            |
| Kubernetes scripts (Minikube, AWS, Azure, GCP) | the `env` list of the `tb-db-setup` pod in `database-setup.yml` |

Remove it again once the upgrade has run.

A normal upgrade never needs it. The new version is recorded only after the schema and data changes succeed, so a run
that fails part-way leaves the old version in place, and the check lets you run the upgrade again once the cause is
fixed.

<Aside type="caution">
  This disables every safety check, not only the version comparison, so it will also let an upgrade run against an
  unsupported version or the wrong edition. Back up your database before using it.
</Aside>
